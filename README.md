# na-lightsail-monitor

一个 Cloudflare Worker，每 10 分钟查一次指定 AWS Lightsail 实例本月已用的流量。两道线任意一道被触碰就把实例停掉：月度总量达到套餐额度的设定比例（默认 80%），或者按最近半小时的速率算、剩余额度撑不过一个反应视野。下个月额度重置后再自动启回来。它防的是 Lightsail 的流量超额账单——那种没有上限、按 GB 计费、要到月底账单上才现身的东西。

约 570 行 JavaScript，唯一的运行时依赖是 4 KB 的 `aws4fetch`。它不提供任何网页界面，也不会主动通知任何人；关于后一点为什么是刻意的、以及你该拿什么来补，见 [AWS Budgets](#5-配置-aws-budgets必做) 一节。

> [!IMPORTANT]
> **适用范围：整个 AWS 账号里只有一台 Lightsail 实例，且长期存在、按月正常扣费。**
>
> 多实例、混合规格、跨可用区、月中创建导致额度按天折算——这些都**不在设计范围内**，本项目不做任何处理。原因和后果见[适用范围](#八适用范围整个账号只有一台长期存在的实例)一节。用之前请先读那一节确认你的情况符合。

## 一、先搞清楚 Lightsail 的额度规则

这些规则决定了代码里每一个数字的含义，写错一条，看门狗守的就是错的东西。

- **进出双向都消耗额度，但只有出向超量才计费**，入向超量免费。所以 Worker 把 `NetworkIn + NetworkOut` 相加来判断，而不是只看出向：额度是被两个方向一起吃掉的。
- **额度在同一区域、同一 `bundleId` 的实例之间汇总。** 同规格的 IPv4 实例与 IPv6 实例计入同一份额度。
- **删掉实例再新建不会重置额度**，已经产生的超额费用也不会消失。
- **月中创建的实例，当月额度按天折算。** 一台 1 号就在的实例拿满 1 TB，20 号才建的只拿到剩余天数对应的那一份。**本项目不处理这种情况**，见[适用范围](#八适用范围整个账号只有一台长期存在的实例)。
- **部分区域的套餐额度只有其它区域的一半**：孟买、悉尼、雅加达、马来西亚、香港、圣保罗。东京（`ap-northeast-1`）是完整额度。
- **超额费率随区域不同**，东京约为每 GB 0.14 美元。

额度在每月 1 日 **00:00 UTC** 重置。Worker 全程用 UTC 计算月份边界，不碰本地时区——两者不是同一个时刻，用错会让每个月有最多一天的时间查错窗口。

## 二、工作原理

一个 cron trigger，`*/10 * * * *`，每天 144 次。每次触发做的事情是固定的：先量，再让数字决定动作。

**贯穿全篇的一条原则：停机路径上的每一个不确定性都向「停」倾斜，重启路径上的都向「什么都不做」倾斜。** 漏停一次的代价是账单，多停一次的代价是站点晚几分钟回来；误启动一台被刻意停下的实例会开始烧流量，少启动一次不会。下面凡是看起来不对称的地方，都是这条原则的结果。

**它是无状态的。** 没有 KV、没有 D1、没有 Durable Object，每次触发都从 Lightsail 指标 API 重新算一遍用量。所以没有会损坏的存储，一次失败的触发之后也没有任何东西需要对账——下一次触发会独立地把结论重新得出来。

**测量。** 用 `GetInstanceMetricData` 分别拉 `NetworkIn` 和 `NetworkOut` 从**本月 1 日 00:00 UTC 到此刻**的数据，`statistics: ["Sum"]`，把所有数据点的 `sum` 累加。数据点既不保证有序也不保证连续，所以是累加而不是按下标取值——求总量与顺序无关，缺口本身就代表那段时间没有流量。

时间基准取的是 `controller.scheduledTime` 而不是墙上时钟：它精确落在 cron 的时间格上，即便这次调用被延迟或重试，评估的仍然是它当初被触发的那一格。

**判断。** 令 `used = (NetworkIn + NetworkOut) / 2^30`，`limit = QUOTA_GIB × THRESHOLD`：

| 情形 | 动作 | AWS 调用次数 |
| --- | --- | --- |
| `used >= limit` | **停机** `StopInstance`，日志写 `console.error`（实例非 `running` 时跳过动作） | **4**（或 3） |
| `used < limit`，突发闸门跳闸 | **停机**，同上 | **6**（或 5） |
| `used < limit`，速率正常 | 什么都不做 | **4** |
| 总字节 **恰为 0**，实例 `stopped` | **启动** `StartInstance` | **4** |
| 总字节恰为 0，实例是别的状态 | 什么都不做 | 3 |
| 总字节恰为 0，但 `MANUAL_HOLD="true"` | 什么都不做，连状态都不查 | 2 |

正常日子的基线是 4 次调用：两个指标的月度查询，加上突发闸门那半小时窗口的两次查询。再往上第 5 次是 `GetInstanceState`，第 6 次才是真正的动作。总量已经越过静态线时会跳过突发闸门——已经确认要停，没必要再花两次调用去问速率。

**突发闸门。** 月初至今是个**滞后的总量**，它看不出「最近半小时正在以 2 Gbps 烧」。默认的 20% 余量在 1 Gbps 下只够烧 29 分钟、2 Gbps 下 15 分钟——并不比一个检测回路长多少。所以除了静态线，每次触发还额外查最近半小时（`period: 300`），算出当前速率，然后问一个动态问题：

> 按这个速率，剩余额度还能撑多久？撑不过 60 分钟就现在停。

比较的目标是**整份额度**而不是 `THRESHOLD` 那条保守的早停线：这道闸门问的是「会不会在下一次能反应过来之前冲过配额」，而配额才是开始计费的地方。60 分钟这个反应视野必须覆盖整个检测回路——桶必须先关闭（≤ 5 分钟）＋ 指标落库延迟 ＋ cron 间隔 10 分钟 ＋ `StopInstance` 真正断流约一分钟。按落库延迟 10 分钟算回路是 26 分钟，60 分钟给到 2.3 倍余量。**改 cron 间隔时必须回来重新审视 `REACTION_HORIZON_SECONDS`**——cron 是回路里最大的一项，见[参数是怎么定的](#参数是怎么定的)。

速率是**两个方向各算各的再相加**：每个指标的字节数除以它自己实际落库的点数 × 300 秒，而不是除以窗口长度，也不是把两个方向合起来除以一个共同的分母。三件事各有理由：

- **不除以窗口长度。** 指标有几分钟延迟，窗口尾部通常还是空的；拿整个 1800 秒去除会把速率算低——而算低正是不安全的那个方向。
- **不用共同分母。** 两个指标的落库进度不保证同步。`NetworkIn` 落了 6 个桶而 `NetworkOut` 只落了 2 个时，取较长的那个当分母，会把出向那 600 秒里的字节摊到 1800 秒上，速率报低三倍——一场 2 Gbps 的突发就这样被放行。
- **也不取较短的那个。** 某个方向一个点都没落时分母会归零，闸门整个失效。

各算各的，两种偏差都不会发生：没有数据点的方向贡献 0，另一个方向照常判断。

窗口取半小时是被两头夹出来的，不是随手取的整数，见[参数是怎么定的](#参数是怎么定的)。

**这张表里最值得注意的是「恰好零字节」那一行。** 它是查询实例状态的闸门：一台运行中的实例几分钟内必然产生*某些*流量——DNS、NTP、互联网上的后台扫描——所以「月初至今总量为零」等价于「它没起来」。没有这道闸门，handler 就得在每个正常日子的每一次触发里都多问一次 `GetInstanceState`，为了每月一次的重启多付约 4300 次 API 调用。总量恰为零时也不可能有突发，所以那两次窗口查询同样省掉。

**停机与重启是幂等的。** 停机前先查状态，所以第二次触发不会对一个已经停下（或正在停）的实例再发一次停机。重启只在总量恰为零且状态为 `stopped` 时发出。

**但那次状态查询不是停机的前置条件。** 一旦确认越线，`GetInstanceState` 读不出结果（HTTP 失败、响应里没有状态名）时会照停不误，只在日志里留一行 `erring toward the stop`。它存在的意义只是幂等，让它的失败中断整轮，等于让一次已经确认的越线白白漏掉一个 cron 周期。

**由此有一个值得知道的后果：你自己在月中停掉的实例不会被它拉起来。** 那时计量表上已经有流量，总量不为零，重启分支根本不会进。它要等到跨月、读数归零之后才会接手这台实例——如果那时你仍然不希望它被启动，就设 `MANUAL_HOLD`。

**错误处理。** 任何非 2xx 的 Lightsail 响应都抛出异常，向上冒到 Workers，把这次调用记为失败；异常消息里会把 access key id 抹成 `[redacted]`（先脱敏再截断，否则 key 正好横跨 500 字节边界时会残留半截），因为 SigV4 的拒绝响应会回显包含它的 credential scope。签名客户端配了 2 次重试，只针对 5xx 和 429；下一次触发在十分钟后，再多重试没有意义。

**读不懂的响应一律抛错，绝不折算成 0。** 这一条专门针对指标：`metricData` 缺失或不是数组时会抛错，而不是当成空数组。理由就是开头那条原则——0 字节是**唯一**会让看门狗什么都不做的读数，把「读不懂」静默折算成 0，就等于让指标侧的一次降级换来一个一边报平安、一边放任实例烧到超额的看门狗。合法的空数组（跨月后本来就没有数据点）照常按零处理。`GetInstanceState` 读不出状态名同理。

## 三、单位：为什么全都是 GiB

`QUOTA_GIB` 填的是 **GiB（2^30 字节）**，直接照抄 `GetBundles` 返回的 `transferPerMonthInGb`：1 TB 套餐填 `1024`，2 TB 填 `2048`，不需要任何换算。

这个结论来自字段命名的一致性推断，而不是 AWS 的明文定义——**AWS 从未说明 `InGb` 这类字段的字节含义。** 推断的依据有两条：

1. `GetBundles` 把宣称的「1 TB」记为 `transferPerMonthInGb: 1024`，2 TB 记为 `2048`，3 TB 记为 `3072`。前缀是按二进制缩放的。
2. 同一份响应里还有 `ramSizeInGb: 0.5`，而 0.5 GB 的内存只可能是 512 MiB（2^29 字节）。

**即便这个推断是错的，默认配置依然安全。** 默认停机线是 `1024 × 0.8 = 819.2 GiB ≈ 879.6 × 10^9 字节`：

- 若 1 TB 指 2^40 字节，停机线占额度的 **80%**；
- 若 1 TB 指 1024 × 10^9 字节，停机线占 **约 85.9%**。

两种解释下都没有超额。这就是这套换算的安全性论证——它不依赖推断成立。

| 套餐 | 宣称额度 | `transferPerMonthInGb` | 填进 `QUOTA_GIB` |
| --- | --- | --- | --- |
| `nano_3_0` | 1 TB | 1024 | `1024` |
| `micro_3_0` | 2 TB | 2048 | `2048` |
| `small_3_0` | 3 TB | 3072 | `3072` |

配置时以 `aws lightsail get-bundles` 在**你的目标区域**返回的实际值为准，不要照抄上表——[部分区域的额度只有一半](#一先搞清楚-lightsail-的额度规则)。

```bash
aws lightsail get-bundles --region ap-northeast-1
```

控制台里也能查到同一个数字：*Lightsail → 实例 → 你的实例 → 网络 → 每月数据传输*。

## 四、配置

两个 secret 用 `wrangler secret put` 设置，其余变量写在 [`wrangler.jsonc`](wrangler.jsonc) 的 `vars` 里。以下是每个变量的权威说明，文档其它地方只做引用。

### Secret（绝不写进 `wrangler.jsonc`）

| 名称 | 说明 |
| --- | --- |
| `AWS_ACCESS_KEY_ID` | IAM 用户的 access key id。 |
| `AWS_SECRET_ACCESS_KEY` | 对应的 secret access key。 |

两者都只做「存在性」检查，值不会离开签名函数，也不会出现在任何日志或异常消息里。

### 变量

| 名称 | 必填 | 说明 |
| --- | --- | --- |
| `AWS_REGION` | 是 | 实例所在的 Lightsail 区域，例如 `ap-northeast-1`。它同时决定 API endpoint 与签名 region。 |
| `INSTANCE_NAME` | 是 | 要监控的实例名（Lightsail 控制台里显示的那个名字，不是 ARN、不是主机名）。它和 `AWS_REGION` 一起构成每行日志的前缀 `实例名@区域`——实例名只在单个区域内唯一，所以两者都要有，日志才能独立说明自己出自哪个部署。 |
| `QUOTA_GIB` | 是 | 套餐的月度流量额度，单位 GiB。必须是正数。取值与含义见[单位](#三单位为什么全都是-gib)一节。 |
| `THRESHOLD` | 是 | 静态停机线：用到额度的这个比例就停机。必须是 **(0, 1] 区间的小数**，`0.8` 表示 80%。写成 `80` 会在启动时被拒绝。设为 `1` 表示**用满整份额度才停**——也就是恰好停在开始超额计费的那一刻，而不是「不再停机」。**没有任何配置值能让实例超额跑下去**，见[设计取舍](#没有运行时的关闭保护开关)。这条线只看月度总量；速率由突发闸门单独管，它不受 `THRESHOLD` 影响。 |
| `MANUAL_HOLD` | 否 | 设为字符串 `"true"` 时抑制所有 `StartInstance`，用于你自己把实例停下来做维护、不希望它被拉起来的场景。**只认精确的 `"true"`**，`"True"`、`"yes"`、`"1"`、前后带空格的都视为未设置。停机行为不受它影响。 |

`AWS_REGION` 与 `INSTANCE_NAME` 还额外拒绝字面值 `CHANGE_ME`——占位符是非空字符串，能骗过「必填项缺失」那道检查，然后每天在 Lightsail 侧失败几百次，留下一堆读不懂的 400（Lightsail 把 NotFound 也归为 400）。这个检查是精确比较：真有人的实例叫 `change_me_later`，那是别人正经的实例名，不能拦。

任何一项校验失败都是硬错误，在发出**任何** AWS 请求之前抛出。原因见[设计取舍](#配置解析失败即硬错误)。

## 五、部署

按下面的顺序做。

### 1. 建 IAM 用户与策略

创建一个只给这个 Worker 用的 IAM 用户，附上下面这份策略，然后生成 access key。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "LightsailBandwidthWatchdog",
      "Effect": "Allow",
      "Action": [
        "lightsail:GetInstanceMetricData",
        "lightsail:GetInstanceState",
        "lightsail:StopInstance",
        "lightsail:StartInstance"
      ],
      "Resource": "*"
    }
  ]
}
```

这四个动作正好是 [工作原理](#二工作原理) 那张表里会出现的全部调用，没有多余的。

`"Resource": "*"` 在本项目的[适用范围](#八适用范围整个账号只有一台长期存在的实例)下是安全的：账号里本来就只有那一台实例，`*` 和精确 ARN 指向的是同一个东西。

之所以不写成精确 ARN，是因为 Lightsail 的资源 ARN 由自动生成的 GUID 拼成（`arn:aws:lightsail:REGION:ACCOUNT:Instance/GUID`）而不是实例名，收窄权限得先查出 ARN 再填回策略，而实例一旦重建 GUID 就变了，策略也得跟着改。**如果你的账号并不符合适用范围——里面还有别的、绝不希望被这套东西碰到的实例——那么收窄这一步就不再是可选项了：**

```bash
aws lightsail get-instance --instance-name your-instance --region ap-northeast-1
```

### 2. 填变量

编辑 [`wrangler.jsonc`](wrangler.jsonc) 的 `vars`，按[配置](#四配置)一节填好 `AWS_REGION`、`INSTANCE_NAME`、`QUOTA_GIB`、`THRESHOLD`。

### 3. 写入 secret

```bash
npx wrangler secret put AWS_ACCESS_KEY_ID
```

```bash
npx wrangler secret put AWS_SECRET_ACCESS_KEY
```

### 4. 部署

仓库已经通过 **Cloudflare Workers Builds** 连接，watch `main` 分支，用本项目专属的 build token。**push 到 `main` 就会自动构建部署**，包括改 `wrangler.jsonc` 里的变量——调 `THRESHOLD` 走的就是「改文件 → push → 自动部署」这条路。

**deploy command 必须是 `npm run deploy`，不能是裸的 `npx wrangler deploy`。** 前者等价于 `npm test && npx wrangler deploy`：测试不过就不部署。这一条不是洁癖——一次坏部署换来的是一个悄悄失效的看门狗，而那正是[下一节](#5-配置-aws-budgets必做)整节在讲的、最难被察觉的故障。仓库里另有一个跑同一套测试的 GitHub Actions，作用是让失败在 commit 和 PR 上直接可见，但它**不会**拦住 Workers Builds——真正的闸门是 deploy command 里那个 `npm test`。

本地部署仍然可用，适合首次部署或紧急发布（同样走带闸门的那条）：

```bash
npm install
```

```bash
npm run deploy
```

到 *Workers & Pages → na-lightsail-monitor → Settings → Triggers* 确认 cron trigger 已生效。日志在控制台可看（`observability` 已开启），也可以直接 tail：

```bash
npx wrangler tail
```

每次触发写**一行**，行首是 `实例名@区域` 加一个状态标记：

```
your-instance@ap-northeast-1 OK | used 137.482 GiB (13.4% of 1024) | stop at 819.200 GiB | now 4.3 Mbps, 20.5 d to quota | month 47% elapsed, projected 294 GiB | meter 1.5 min behind
```

状态标记是给 grep 用的。想只看值得关注的事件：

```bash
npx wrangler tail --format pretty | grep -v " OK | "
```

| 标记 | 含义 | 级别 |
| --- | --- | --- |
| `OK` | 两道线都没碰到 | log |
| `STOPPED` | 已停机。后面跟着触发的是静态线还是突发闸门 | **error** |
| `STARTED` | 额度读数归零且实例处于停机，已启动 | log |
| `NOOP` | 该做的事已经是既成事实（越线但实例已停、读数为零但实例在跑） | log |
| `HOLD` | 本该启动，但 `MANUAL_HOLD` 拦住了 | log |
| `BLIND` | 突发闸门这一轮看不见东西，见下 | **error** |
| `DEGRADED` | 状态查询失败，但已经确认越线，照停不误 | **error** |

`OK` 那一行的每个字段各回答一个问题，而且全部是这一轮**已经算出来**的东西，没有为日志多花任何一次 API 调用：

| 字段 | 回答的问题 |
| --- | --- |
| `used 137.482 GiB (13.4% of 1024)` | 我在哪 |
| `stop at 819.200 GiB` | 线在哪 |
| `now 4.3 Mbps, 20.5 d to quota` | **突发闸门这一轮读到了什么。** 不露出来的话它在正常运行里完全不可见，没人能确认它还在正常工作 |
| `month 47% elapsed, projected 294 GiB` | 照这个月的平均速度，整月会用到多少。月初 15 小时内样本太短，这个字段会省略 |
| `meter 1.5 min behind` | 上游数据有多新——整套余量标定唯一一个没有文档的输入，见[上游 API 的精度与延迟够不够](#上游-api-的精度与延迟够不够) |

几个值得认识的读数：

- `now 0 kbps, never to quota`——最近半小时确实没有流量。
- `now 143.2 Mbps (stale), ...`——**速率带 `(stale)` 标记**，说明数据老过了容忍上限（12 分钟），同一轮里必定还有一条 `BLIND`。这个数不能当正常读数看。
- `projected 1497 GiB`——静态线还没碰到，但趋势已经越过 1024 的额度了。这是最早能看出问题的字段。

**部署后第一件该确认的事，就是 `OK` 那一行末尾的 `meter ... behind` 真的出现了。** 它是从数据点的时间戳算出来的；如果它一直不出现，说明 Lightsail 返回的时间戳不是 Unix 秒（代码只认数字，认不出就静默略过这段），那么[上游 API 的精度与延迟够不够](#上游-api-的精度与延迟够不够)那一节的全部结论都还没有被验证过。闸门本身不受影响——速率计算不碰时间戳——但你就失去了唯一那个能校准余量的读数。

这条通道是单向的：日志只会待在那里等你去看，不会来找你。下一步就是补上那个会主动来找你的东西。

### 5. 配置 AWS Budgets（必做）

**这个 Worker 不会主动通知任何人，这是刻意的。** 停机时它写一行 `console.error`，任何失败以异常向上抛出、由 Workers 记为失败——两者都只留在日志里，而日志是需要你主动去拉的次要信号。

真正需要讲清楚的不是「停机了我怎么知道」，而是**看门狗自身失效时你怎么知道**：

- AWS 凭据过期或被轮换
- IAM 用户被删、策略被改
- 部署损坏、`wrangler.jsonc` 改错
- cron trigger 被禁用
- Worker 被整个删掉

每一种情形都让实例继续运行、继续消耗流量，而**从外部看，它与「本月流量很平静」完全无法区分**。Worker 说不出这件事，因为它自己就是坏掉的那一方。任何由这个 Worker 自己发出的告警都覆盖不了这一类故障。

**AWS Budgets 是唯一覆盖这一情形的信号，必须配置。** 它由 AWS 依据自己的账单数据触发，与这个 Worker 是否存活完全无关。

> 账单与成本管理 → 预算 → 创建预算 → 成本预算

金额设成略高于正常月度支出（一台 5 美元实例在没有超量时约 5 美元，预算可以设 10 美元），在 **80% 和 100%** 两个点告警到**一个你真的会看的邮箱**。

代价是慢：AWS 的账单数据有数小时延迟，等它响的时候钱已经花了一部分。所以它是安全网，不是替代品——Worker 负责在超额之前就把闸拉下来，Budgets 负责在 Worker 没能做到这件事时告诉你。

**再补一个快的：Lightsail 自带的实例指标告警。** Budgets 以小时计，而一台跑满 1 Gbps 的实例半小时就能烧掉默认余量。Lightsail 控制台里可以直接对实例的 `NetworkOut` 设阈值告警，几分钟内就会发邮件：

> Lightsail → 实例 → 你的实例 → 指标 → 网络出 → 添加告警

阈值按「一个 5 分钟数据点的字节数」设，取一个正常业务绝不会碰到的值即可。它和 Budgets 一样由 AWS 侧触发，**与这个 Worker 是否存活无关**，但快得多。三者是互补的，各自守着不同的失效：

| | 谁在判断 | 延迟 | 覆盖 |
| --- | --- | --- | --- |
| Worker 的静态线 | Worker | 分钟级 | 月度总量爬到阈值 |
| Worker 的突发闸门 | Worker | 分钟级 | 速率突然拉高 |
| Lightsail 指标告警 | AWS | 分钟级 | 速率突然拉高，**且 Worker 已经死了** |
| AWS Budgets | AWS | 小时级 | 钱已经花出去了，**且上面三道全都没拦住** |

## 六、设计取舍

这一节解释的是「为什么不那样做」。

### 重启由用量驱动，而不是按日期

停机只发生在用量越线时，所以当月剩下的时间里用量会一直卡在阈值之上。「用量回落到阈值以下」与「每月 1 号」捕捉的是同一个事件，但前者没有那个仅 24 小时的窗口。

按日期驱动的版本有个安静的失效模式：如果 1 号那天恰好凭据过期、或者 AWS 抽风，重启就错过了，实例一直停到下个月。用量驱动下，跨月之后**每一次触发**都是一次新的补救机会。

### 「恰好零字节」作为查询状态的闸门

见[工作原理](#二工作原理)。一句话：它省掉了正常路径上的 `GetInstanceState`，每月约 4300 次调用，代价是一个在物理上不可能误判的假设——运行中的实例产生零字节流量。

这个假设有个前提：指标响应本身是可信的。所以指标读不懂时必须抛错而不是折算成 0——否则「零字节」就不再只意味着「它没起来」，还可能意味着「我没看清」。这两件事必须分开，见[错误处理](#二工作原理)。

### `MANUAL_HOLD` 与 `"true"` 精确比较

打错字时（`"True"`、`"yes"`、`"1"`）重启逻辑仍然有效。方向是刻意选的：一个失效时默认放行的锁是可以补救的；而一个因为笔误就生效的锁，会把实例摁在那里，直到有人发现站点不见了。

### `THRESHOLD` 必须是 (0, 1] 的小数

上界卡在 1，是为了让「按百分比写成 `80`」在启动时就被拒绝。不校验的话它会变成 81,920 GiB 的停机线——一个永远够不到的上限，也就是一个看起来在跑、实际上什么都不做的看门狗。

### 配置解析失败即硬错误

`Number("1,024")` 是 `NaN`，而**与 `NaN` 的任何比较都是 false**。`used < limit` 为 false 会被后续逻辑读作「已超额」，于是这台实例会被立刻停掉。所以每一个数值变量都必须在第一次触发时大声失败，而不是套用某个静默的默认值继续跑。

### 没有运行时的「关闭保护」开关

**一旦越线，就没有任何办法让实例照常跑下去**，这是刻意的。`MANUAL_HOLD` 抑制的是启动而不是停机，所以它救不了场；手动去控制台把实例启动起来，也只能换来十分钟——下一次触发会把它按回去。

**说清楚一点：`THRESHOLD = 1` 不是「不再停机」，是「用满整份额度才停」**——恰好停在开始超额计费的那一刻。这已经是能配出来的最宽松的一档；再往上会被启动时的校验拒绝。如果你确实决定「宁可认了这笔超额费用，也不能让站点下线」，那么**这个配置项给不了你想要的东西**，唯一的办法是改代码或者把 cron trigger 停掉——两件都会留在 `git log` 或 Cloudflare 的配置历史里。

突发闸门也不受 `THRESHOLD` 影响：它比较的是整份额度，所以即便把 `THRESHOLD` 设成 `1`，一次会在半小时内冲过配额的突发照样会被拦下。

运行时开关会友好得多。但**一个能关掉保护的开关，就是一个会被忘记打开回来的开关**；而一个从三月起就被悄悄禁用、无人看管的账单护栏，恰恰是这个 Worker 存在所要防止的场景。

改文件再部署确实麻烦，而这正是重点——它难以被随手做掉，它会留在 `git log` 里，那个 diff 会一直显得不对劲，直到有人把它改回来。

### 停机不是应用层的优雅关闭

`StopInstance` 从实例角度看等同于断电。如果工作负载需要把状态刷到磁盘，就把 `THRESHOLD` 设低一些，给自己留出反应余地。

### 安全裕度由 `THRESHOLD` 和突发闸门共同提供，绝不来自单位换算

想要更大的静态余量就调低 `THRESHOLD`，**不要靠单位换算制造缓冲**。藏在换算里的缓冲既写不进配置，也读不出来——半年后没人能说清那个数字是怎么来的。

两道线守的是不同的东西，缺一不可：`THRESHOLD` 守「爬得慢但爬到了」，突发闸门守「爬得快」。单独调低 `THRESHOLD` 换不来对突发的防护，因为静态线无论设多低，都要等**总量**先越过它。

### 余量必须按「能被多快烧掉」来标定，而不是取个好看的百分比

这是整个项目里最容易被想当然的一处。默认的 20% 余量在 1 TB 套餐上是 204.8 GiB，听起来很宽裕，但它到底够不够，取决于实例能跑多快：

| 持续速率 | 烧完 204.8 GiB 余量 |
| --- | --- |
| 100 Mbps | 4.9 小时 |
| 250 Mbps | 2.0 小时 |
| 500 Mbps | 58.6 分钟 |
| 1 Gbps | 29.3 分钟 |
| 2 Gbps | 14.7 分钟 |
| 5 Gbps | 5.9 分钟 |

而一个完整的检测回路是：cron 间隔（2 分钟）＋ 指标落库延迟（几分钟）＋ 停机生效（约一分钟）。**在 1 Gbps 上，一个回路就要吃掉余量的相当一部分；在 2 Gbps 上，静态线根本来不及触发。** 这正是突发闸门存在的理由——它不等总量越线，直接问「按现在的速率还剩多久」。

如果你的实例能跑得比这更快，两个旋钮都要动：调低 `THRESHOLD`，并缩短 cron 间隔（同时复核 `REACTION_HORIZON_SECONDS`）。

### 参数是怎么定的

四个可调的数，各自被什么夹住。前提是一台 1 TB 套餐的实例，指标落库延迟按 10 分钟的悲观值算。

**`THRESHOLD = 0.8`（静态线）。** 不能再高，因为[单位](#三单位为什么全都是-gib)那一节的安全性论证依赖它：

| `THRESHOLD` | 停机线 | 若 1 TB = 2^40 | 若 1 TB = 1024×10^9 |
| --- | --- | --- | --- |
| 0.80 | 819.2 GiB | 80.0% | **85.9%** |
| 0.85 | 870.4 GiB | 85.0% | 91.3% |
| 0.90 | 921.6 GiB | 90.0% | **96.6%** |

`InGb` 到底是十进制还是二进制，AWS 从没说过。0.8 在两种解释下都留着余量；0.9 在悲观解释下只剩 3.4%，连指标延迟都盖不住。

反过来也不该调低：**静态线触发不算「过早停机」**——它响的时候你确实已经用掉了 80% 的额度。真正可能误停的是突发闸门，那是另一个旋钮的事。

**`REACTION_HORIZON_SECONDS = 3600`（视野）。** 这是闸门唯一的灵敏度旋钮，判据等价于 `速率 > 剩余额度 ÷ 视野`。60 分钟意味着空表时要约 2.4 Gbps、用到 800 GiB 时要约 534 Mbps 才跳闸——对一台个人站实例，两个数仍然远在正常业务之上。**想更保守就调大它**，代价是可能掐掉一次合法的大流量传输（备份、迁移、直播）。

这个数是**跟着 cron 走的**，不是独立选的。检测回路 = 桶关闭（≤ 5 分钟）＋ 落库延迟 ＋ cron 间隔 ＋ 停机生效（约 1 分钟）：

| 落库延迟 | cron 每 2 分钟的回路 | cron 每 10 分钟的回路 | 30 分钟视野的余量 | 60 分钟视野的余量 |
| --- | --- | --- | --- | --- |
| 5 分钟 | 13 分钟 | 21 分钟 | 1.43x | 2.86x |
| **10 分钟** | 18 分钟 | **26 分钟** | **1.15x** | **2.31x** |
| 15 分钟 | 23 分钟 | 31 分钟 | **0.97x —— 守不住** | 1.94x |
| 20 分钟 | 28 分钟 | 36 分钟 | 0.83x | 1.67x |

`*/2` 时 30 分钟够用；改成 `*/10` 之后回路涨到 26 分钟，同样的 30 分钟只剩 1.15 倍，而落库延迟一到 15 分钟就**跌破 1.0**——额度会在闸门能动手之前烧完。所以这次把视野提到了 60 分钟。**两个数是一起变的，不能只改一个。**

**`BURST_WINDOW_SECONDS = 1800`（观察窗口）。** 两头夹出来的：

- **太长会稀释。** 速率是窗口内的平均值，刚开始 5 分钟的突发在一小时的窗口里只显出真实速率的十二分之一。闸门会在「距离额度耗尽还剩 `H/(H+W−L)`」处跳闸，与速率无关：

  | 窗口 | 跳闸时耗尽进度 | 5 Gbps 下剩余余量 | 延迟 20 分钟时还剩几个数据点 |
  | --- | --- | --- | --- |
  | 60 分钟 | 63% | 7.2 分钟 | 8 |
  | **30 分钟** | **40%** | **11.6 分钟** | **2** |
  | 20 分钟 | 25% | 14.5 分钟 | **0 —— 闸门失效** |

- **太短会瞎。** 窗口整个落进落库延迟的阴影里就一个数据点都没有。

30 分钟是这两条曲线的交点。**它只影响反应快慢，不影响灵敏度**——判据里没有 `W`，所以缩短窗口不会让闸门更容易误报。这就是为什么「想更保守」要去动视野而不是窗口。

**cron `*/10`。** 频率本身在两边都几乎免费，但更低的频率不是出于额度：

| cron | 次数/天 | 占 Workers 10 万次/天额度 | AWS 侧调用/天 | AWS 侧调用/月 |
| --- | --- | --- | --- | --- |
| **`*/10`** | **144** | **0.14%** | **576** | **17,856** |
| `*/1` | 1440 | 1.44% | 5,760 | 178,560 |

两边的额度都远远够用——Workers 免费版每天 10 万次请求，而 **Lightsail API 调用不计费、也没有任何速率配额**（详见[Lightsail API 的坑](#九lightsail-api-的坑)）。选 `*/10` 而不是更快，是因为**不希望高频轮询被上游判定为滥用接口**——那不是一条能在文档里查到的线，所以宁可留出余量。代价是检测回路从 18 分钟涨到 26 分钟，由视野从 30 分钟提到 60 分钟补回来。

`*/1` 也完全付得起，但检测回路是被指标延迟主导的（几分钟），把 cron 从 2 分钟压到 1 分钟只能省下约 1 分钟，不值得把调用量翻倍。免费版每次调用 10 ms CPU、50 个子请求的限制，在 4 次调用下都很宽裕；日志约 720 条/天，也远低于免费额度。

**改动时的联动**：cron 是检测回路里最大的一项，所以改 cron 必须回来复核视野，反之亦然。上面那张表就是这次从 `*/2` 改到 `*/10` 时重算的依据。

### 指标是有延迟的

Lightsail 的指标比真实流量晚几分钟落库，所以观察到的用量总是落后于实际用量。这条延迟在三个地方被明确处理过：反应视野把它算进了余量；突发闸门的速率按每个方向**各自**实际落库的点数计算，而不是窗口长度、也不是共同分母；以及日志里那个 `meter ... behind`，它把这条延迟从假设变成了每次触发都能看到的实测值。

### 停机路径 fail-closed，重启路径 fail-open

同一个 `GetInstanceState` 失败，两条路径的处理是相反的，这是刻意的：

- **已经确认越线**时读不到状态 → **照停**。多发一次停机的代价是一条错误日志。
- **打算重启**时读不到状态 → **不启动，抛错**。误启动一台被刻意停下的实例会开始烧流量。

同样的道理适用于读不懂的指标响应：它在停机方向上是致命的（0 字节 = 一切正常），所以宁可整轮失败。

### 上游 API 的精度与延迟够不够

这套东西的反应速度上限不由我们决定，由 Lightsail 的指标 API 决定。两个上游参数：

**采样精度：300 秒，已经触底。** 除 `StatusCheckFailed*` 外，所有实例指标只有 5 分钟这一档粒度。所以 `BURST_PERIOD_SECONDS = 300` 不是一个选择，是硬件上限——`period` 填 60 只会得到空桶。**我们能看到的最快的东西，就是一个 5 分钟平均值。**

**落库延迟：AWS 不公开。** 官方原话只到「数据点不会在周期结束的那一刻就可查，具体多久随服务而变」。这是个问题，因为上面所有的余量标定都以它为输入。**所以 Worker 自己量**：突发窗口那次查询本来就要拉数据点，取最新那个桶的时间戳，减一下就是延迟，零额外调用，每次触发都写进日志。

由此可以算出**不可压缩的盲区**：

> 桶必须先关闭（≤ 300 秒）＋ 落库延迟 L ＋ cron 间隔（≤ 600 秒）＋ 停机生效（约 60 秒）

即便 L 为零，也有 **16 分钟**看不见。**任何参数都调不到这个下限以下**，而 cron 从 2 分钟放宽到 10 分钟，正是把这个下限从 8 分钟抬到了 16 分钟。把它换算成实际后果（从空表开始的突发，额度 1024 GiB，视野 60 分钟）：

| 落库延迟 L | 只有静态线时烧掉 | 加上突发闸门后烧掉 | 闸门可用桶数 |
| --- | --- | --- | --- |
| 5 分钟 | 1465 GiB **超额** | 809 GiB | 5 |
| 10 分钟 | 1640 GiB **超额** | 902 GiB | 4 |
| 15 分钟 | 1815 GiB **超额** | 1008 GiB | 3 |
| 20 分钟 | 1989 GiB **超额** | 1129 GiB **超额** | 2 |
| 25 分钟 | 2164 GiB **超额** | 1269 GiB **超额** | 1 |
| 30 分钟 | 2338 GiB **超额** | 2338 GiB **超额** | 0 |

（按 5 Gbps 算——这是 2023-06-29 之后创建的 Lightsail 实例的文档上限。）

三个结论：

1. **在几百 Mbps 这一档，静态线单独就够。** 1 Gbps 时越过阈值后最坏再烧约 164 GiB，204.8 GiB 的余量仍然吃得下——但比 `*/2` 时的 101 GiB 明显吃紧了。
2. **在 Gbps 这一档，静态线单独必定超额，突发闸门是唯一拦得住的东西。** 上表左右两列的差距全部来自它。
3. **延迟到 30 分钟时闸门彻底失明**（窗口里凑不出一个数据点），防线退回静态线。但**告警不能等到那时才响**——上表显示闸门在延迟 16 分钟就已经守不住了，所以容忍上限取 12 分钟。日志里那条 `newest metric bucket is ... past the 12 min tolerance` 是硬信号，不是噪音。

> [!WARNING]
> **这个门槛必须挂在检测回路上，不能挂在观察窗口上。** 早先它写成「窗口里凑不出两个数据点」= 20 分钟：cron 每 2 分钟时临界点在 25 分钟，20 分钟的告警是**提前**的，没问题；cron 放宽到 10 分钟后临界点降到 16 分钟，同一个 20 分钟就变成**迟到四分钟**——延迟落在 [16, 20) 分钟这一段时，设计已经失效而没有任何提示。窗口管的是分辨率，回路管的是及时性，两者会在改 cron 时朝不同方向走。

**这套设计成立的条件是 L < 约 18 分钟**（`*/2` 时是 25 分钟）。放宽 cron 的代价就记在这里：**用大约 7 分钟的落库延迟容忍度，换掉了高频轮询被上游看成滥用的风险。** 视野从 30 分钟提到 60 分钟已经把大部分损失补了回来——不提的话条件会是 L < 12 分钟。 这个条件目前没有被验证过——它就是日志里那个 `meter ... behind` 存在的理由。跑上一天，看它的实际分布，再回来对着上表决定要不要动参数。

**真要防住 5 Gbps 级别的攻击，护栏不该只放在这里。** 上游 API 从物理上就喂不动一个那么快的控制环——8 分钟的盲区下限摆在那里。那一档的正确做法是在实例前面加限速（Cloudflare 代理、防火墙规则），把 Worker 留作最后一道兜底。

## 七、Workers 免费版的硬约束

代码里有三处形状是被运行环境直接决定的，改之前先知道原因。

- **只有一个 cron trigger。** 免费版每账号只允许 5 个，这个账号已经有 3 个用于其它项目。所以重启逻辑是在同一个 handler 内部分支处理的，而不是再占一个 trigger。受限的是 trigger 的**个数**，不是频率——`*/10` 一天 144 次，对免费版每天 10 万次请求的额度来说可以忽略，Lightsail API 调用也不单独计费。频率在额度上是免费的，但它决定检测延迟，也决定会不会被上游看成滥用。
- **月度查询的 `period` 取 86400（一天）而不是 3600（一小时）。** 免费版每次调用的 CPU 时间是 10 ms。按天粒度，「月初至今」每个指标返回约 31 个数据点；按小时会返回约 744 个，光解析那份 JSON 就会撑爆 CPU 预算。突发闸门那半小时的窗口用 `period: 300`，每个指标最多 7 个点，解析成本可以忽略——正常触发一共解析四份响应，仍然远在预算之内。
- **`workers_dev` 与 `preview_urls` 都关掉。** 这个 Worker 没有 `fetch` handler，公开 URL 只会返回错误——还会给一个专门用来压低流量的东西招来流量。

## 八、适用范围：整个账号只有一台长期存在的实例

这不是「已知限制，以后会修」，是**设计前提**。不符合就别用，或者先改代码。

### 前提

1. **整个 AWS 账号里只有一台 Lightsail 实例。** 不是「该区域该规格只有一台」——就是一台。
2. **它长期存在，按月正常扣费。** 不在月中创建、不删了重建。

### 明确不在范围内

| 情况 | 为什么不做 |
| --- | --- |
| 账号里有多台实例 | 额度按「区域 + `bundleId`」汇总，而 Worker 只读 `INSTANCE_NAME` 那一台。要正确统计就得先 `GetInstances`、再按区域和规格分组求和，还要处理每组各有一份额度、各需一条停机线——这套东西的复杂度远超它守的那笔钱。 |
| 混合规格 | 同上。不同 `bundleId` 各有各的额度，等于要同时维护 N 条独立的防线。 |
| 跨可用区 / 跨区域 | 同一区域内换 AZ 不影响额度汇总，等价于多实例；跨区域则是另一份额度、另一个 endpoint，需要另一个部署。 |
| 月中创建实例 | 当月额度按天折算，而 `QUOTA_GIB` 是个静态值，它不知道这件事——那个月的停机线会偏高。 |
| 第一个月额度没发满 | 同上，属于同一类问题。**不管。** |

这些都是可以做的，只是复杂度和收益不成比例。本项目选择把范围收窄到「一台、长期、按月」，然后在这个范围内把事情做扎实。

### 打破前提的后果

**读数会低估，而且是静默的。** 这是所有失效模式里最难察觉的一种：

- 静态线和突发闸门读的是**同一个**被低估的数字，所以两道防线会一起失效，不存在互相兜底。
- 它不像别的故障那样会在日志里留痕。你会看到一行行「一切正常」，直到账单出现。
- Worker 自己说不出这件事——它看到的世界里确实只有那一台实例。

这也是[为什么 AWS Budgets 是必做项](#5-配置-aws-budgets必做)：它按整个账号的真实账单触发，不依赖 Worker 对世界的认知是否正确。

**开第二台实例之前，先回来读这一节。**

## 九、Lightsail API 的坑

改代码之前值得知道的几件事，每一件都曾经或可能悄悄地把事情弄错：

- **请求字段是小驼峰**（`instanceName` 而不是 `InstanceName`），与多数 AWS JSON API 相反。写错只会得到一个毫无提示意义的 400。
- **时间戳走 Unix 秒**，不是 ISO 字符串。多乘或少乘一个 1000 是这里的经典 bug——秒级时间戳是 10 位，毫秒级是 13 位。
- 协议是 **JSON 1.1**，靠 `X-Amz-Target: Lightsail_20161128.{Operation}` 分发操作，不是靠 URL path。
- **`NetworkIn` / `NetworkOut` 的单位是字节**，按 5 分钟间隔上报，最有用的统计量是 `Sum`。**300 秒是原生粒度，也是分辨率的硬底**——除 `StatusCheckFailed*` 外所有实例指标都只有这一档，`period` 填 60 不会得到更细的数据，只会得到一堆空桶。
- **数据点保留期随粒度变化**：60 秒粒度 15 天，300 秒粒度 63 天，3600 秒粒度 455 天。本项目两个窗口（30 分钟 @300s、当月 @86400s）用的底层数据都是 300 秒那一档，63 天的保留期绰绰有余。
- **落库延迟没有文档。** AWS 只说「数据点不会在周期结束的那一刻就可查，具体多久随服务而变」，官方给告警的建议是把评估窗口拉宽来容忍迟到的数据。这个数是本项目唯一一个来自上游、又无法查证的输入，所以 Worker 每次触发都会自己量一遍并写进日志。
- **`period` 必须是 60 的倍数**，范围 60–86400。本项目用两个：月度查询取上限 86400，突发闸门取 300，原因见[上一节](#七workers-免费版的硬约束)。
- **空数据不是错误，而且「空」有两种长相。** 窗口内没有流量时 HTTP 仍然是 200，但响应可能返回 `metricData: []`，**也可能把这个字段整个省掉**——AWS 的响应定义没有保证它必然出现，各语言 SDK 一律把「字段缺失」正规化成空数组。所以判断「这份响应读不懂」绝不能挂在 `metricData` 存不存在上；本项目改挂在 `metricName` 是否正确回显上（有值的标量必然被序列化，不像空集合那样可省），两个信号有其一就认定响应是真的。把「字段缺失」当成错误的代价是致命的：一台停机的实例在新月份读到的正是这种空响应，于是每次触发都抛错，重启永远发不出去。
- **Lightsail API 调用不计费。** 计费 FAQ 逐项列举了全部收费项——实例套餐、数据库、块存储、负载均衡器、证书、静态 IP、域名、DNS 查询、快照——**没有 API 请求这一项**，指标与监控也完全没有作为收费项出现。唯一按请求计费的是 DNS 查询（每月 300 万免费，之后 $0.40/百万），与本项目无关。
- **`GetInstanceMetricData` 不会带来 CloudWatch 账单。** CloudWatch 确实按 $0.01/1000 次收 `GetMetricStatistics` 这类请求的钱，但那是 CloudWatch 服务自己的 API；本项目调的是 `lightsail:GetInstanceMetricData`，走的是 Lightsail 的计费口径。（这条值得确认一下：本项目每月约 89,000 次调用，若按 CloudWatch 费率折算是 $0.89/月，对一台 5 美元实例是 18%。）
- **没有任何 API 速率配额。** Lightsail 的服务配额表里 19 项全是资源数量（实例、磁盘、分发、DNS 区域……），没有「每秒请求数」之类的条目。本项目的速率是 **0.033 次/秒**，任何隐含阈值都不会碰到。
- **状态码有两份说法，而且都要认。** 按操作的错误列表把 `AccessDeniedException` 记为 **400**，Common Errors 那份记为 **403**；`NotFoundException`/`InvalidInputException`/`OperationFailureException` 是 400，`ServiceException`/`InternalFailure` 是 500，`ServiceUnavailable` 是 503。签名客户端「只重试 5xx 和 429」的策略在这三档上都是对的：400 与 403 都是终局失败，重试只是浪费时间。
- **但有两个瞬时错误落在重试之外**：`ThrottlingException` 是 **HTTP 400**（AWS 自己都注明「SDK 会自动重试这个异常」），`RequestTimeoutException` 是 **408**——两者都不满足「5xx 或 429」，于是会直接抛出。**这是刻意接受的**：本项目的速率离任何限流阈值有三个数量级，而代价只是丢掉一个 cron 周期（2 分钟）——handler 是无状态的，下一次触发会把结论独立重新得出来，静态线还有 204.8 GiB 余量兜着。真发生了日志里会写明 `HTTP 400 {"__type":"ThrottlingException"...}`，一眼可辨。
- **`instanceName` 有格式约束**：`\w[\w\-]*\w`，也就是首尾必须是单词字符、中间可含连字符。本项目**不**在 `readConfig` 里校验它——AWS 那个 `\w` 是否含 Unicode 无从确认，照着猜写一条正则，风险是把一个 AWS 明明接受的实例名挡在门外，而那正是[占位符检查](#四配置)刻意避免的错误。写错名字会在第一次触发时以 400 失败，是响亮的。

## 十、测试

```bash
npm test
```

78 个用例，跑在裸 `node --test` 上，纯逻辑，不联网，不碰 AWS。`test/scheduled.test.js` 打桩 `globalThis.fetch` 端到端地跑整个 handler——请求确实经过 `aws4fetch` 真实签名，但没有任何东西离开本进程。

打桩按 `period` 区分月度查询和突发窗口，两者能分别给量。这一点是必需的：否则「本月用了 800 GiB」会被当成「最近半小时烧了 800 GiB」，突发闸门在每个用例里都会误触发。

### 四层，各自回答不同的问题

**第一层：例子测试**（`month.test.js`、`scheduled.test.js`）。逐条锁住具体行为。

有几条锁的是**失败的方向**而不是成功路径，它们是这套东西最该被守住的性质：

- 指标响应读不懂时抛错，而不是折算成 0（合法的空数组仍然按零处理）
- 已经越线时状态读不出来，照停不误
- 打算重启时状态读不出来，抛错而不是启动
- 突发速率按每个方向各自实际落库的点数计算，不按窗口长度，也不用共同分母
- 某个方向零数据点时贡献 0，而不是让整个闸门失效
- 每一行日志都以 `实例名@区域` 加状态标记开头，换个区域就是另一个标识
- 速率来自过旧数据点时必须带 `(stale)` 标记，不能装成正常读数

**第二层：性质测试**（`invariants.test.js`）。分两类。

**单调性与无状态**——把两次运行排起来比，断言的是需求里那些「方向」性质：

- 用量越高，绝不该更不容易被停机
- 最近速率越高，绝不该更不容易被停机
- `THRESHOLD` 越低，绝不该更不容易被停机
- 同一格 tick 判两次，结论必须一致（锁住「无状态」这条承诺——哪天有人加了个模块级缓存，「一次失败的触发之后没有任何东西需要对账」就悄悄不成立了）

> **诚实标注：这四条目前没有独立的检出贡献。** 加进来时的设想是「比较符号写反在单点上看不出来，必须排序才露馅」，但做归因实验后发现不成立——注入符号翻转时，率先变红的是一批例子测试；注入一个刻意构造的**非单调**缺陷（只在 `[停机线, 额度×1.05)` 这一段停机、超过就放行）时，抓到它的是随机场景那一层，单调性反而没抓到（用量超过额度后突发闸门的剩余额度变负、顺带跳了闸）。
>
> 留着它们，是因为它们把这几条方向性需求明确写了下来、成本也低；但**不能把它们算进「这套测试有多强」的证据里**。

**随机场景**。前面几轮 review 的方法都是「我想到什么就查什么」，于是每换一个视角就冒出新问题——那说明靠人列举组合根本不够。这一层反过来做：随机生成 1500 个场景，断言一组**从需求推出来、而不是从实现抄下来**的不变量。

生成是**分层轮转**的，不是纯随机：`restart / boundary / burst / failure / random` 各占五分之一。原因是纯随机下「`MANUAL_HOLD` 且用量为零且实例 stopped 且没注入故障」这类组合的概率只有约 0.2%，靠加大样本量去赌是不可靠的。生成的维度包括 AWS 侧失败（400 与 500 分开——只有 500 会被重试）、畸形响应、精确落在停机线上的用量、两个方向落库进度悬殊。

断言的不变量：越线且实例在跑必须停机、启动只在「用量为零 + stopped + 无 hold」时发生、绝不同时停机与启动、凭据绝不出现在任何日志行或异常消息里、畸形响应必须**有意地**抛错（TypeError 不算——那只是碰巧崩了）、评估的窗口必须对应 `scheduledTime`、逻辑操作不超过 6 个且每个最多 3 次 HTTP 尝试。

**第三层：调参耦合检查**（`tuning.test.js`）。这几个数不是各自独立的：cron 间隔、反应视野、观察窗口、延迟容忍上限彼此约束。改了 cron 却忘了视野，代码照样跑、行为照样对、其它测试照样绿——只是防线悄悄变薄。**本项目真的这样错过一次**：cron 从两分钟放宽到十分钟后，延迟告警的门槛还挂在观察窗口上，于是它从「提前五分钟」变成了「迟到四分钟」。

cron 写在 `wrangler.jsonc`、常量写在 `src/index.js`，跨文件的耦合最容易失修，所以这一层把两个文件直接读进来一起验：

- 反应视野 ≥ 2 × 检测回路（回路含 cron 间隔）
- 延迟容忍上限 ≤「视野一半减去回路里的固定部分」——告警必须早于设计失效
- 延迟容忍上限 ≤ 窗口分辨率的失效点
- 容忍上限的延迟下，窗口里仍能凑出至少两个数据点
- 两个 `period` 都落在 API 接受的 60–86400 且是 60 的倍数

三种断裂都实测过会变红：把 cron 放宽到 `*/30`、把视野调回 30 分钟、把容忍上限退回 20 分钟。

**第四层：变异测试**（`npm run mutate`）。

```bash
npm run mutate
```

**这一层存在的理由是：「测试通过」证明不了测试有用。** 这个仓库里出现过两次真实的反例——一次是打桩把 AWS 的合法空响应当成畸形响应，夹具和断言互相印证了同一个错误假设；一次是性质测试跑得很热闹，注入六个已知缺陷却一个都没抓到。

它往 `src/index.js` 里注入 19 个已知缺陷（把速率改回共同分母、静态线 `>=` 改成 `>`、只脱敏 access key id、去掉 `QUOTA_GIB` 上界、把视野调回与 cron 不匹配的旧值……），跑**整个**套件逐个确认会变红——只跑其中一层等于给另一层的覆盖打了白条。有变异存活就退出非零——那说明测试覆盖不到它代表的那类缺陷。

三条纪律都是踩过坑之后加的：全程在临时副本里操作（曾有一次中断把变异留在了 `src/` 里）；先跑对照组（干净代码必须是绿的，否则检测器本身在瞎报）；用 `grep -q` 而不是数行数（reporter 会把失败行打两遍，按等于 1 判断会让每个变异都被误报成「漏过」）。

`test/month.test.js` 刻意把时区设成 `America/Los_Angeles`。每条断言都是针对精确的 epoch 值写的，所以它们在任何时区下都成立；但**一个改用本地时间辅助函数的实现，在 `TZ=UTC` 下会碰巧通过**。正是这个时差让这些测试具备鉴别力。

## 十一、目录结构与依赖

```
src/index.js              Worker 本体
test/                     单元测试（node:test，不依赖测试运行器）
wrangler.jsonc            cron trigger、vars、observability
.github/workflows/test.yml  CI：让测试失败在 commit 和 PR 上可见
```

唯一的运行时依赖是 [`aws4fetch`](https://github.com/mhart/aws4fetch)，版本钉死在 `1.0.20`，约 4 KB，负责完成 SigV4 签名。AWS SDK 对一个 Worker 来说太大了。

纯 JavaScript 加 JSDoc 类型标注，除 Wrangler 原生处理之外没有任何构建步骤。

代码里的日志文本与错误消息保留英文——它们会和 Workers 控制台、AWS 返回的英文报错混在一起，保持一致更便于检索。测试用例名同理。文档正文用中文。
