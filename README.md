# na-lightsail-monitor

一个 Cloudflare Worker，每 10 分钟查一次指定 AWS Lightsail 实例本月已用的流量，两道线任意一道被触碰就把实例停掉；下个月额度重置后再自动启回来。

它防的是 **Lightsail 的流量超额账单**——那种没有上限、按 GB 计费、要到月底账单上才现身的东西。

| | 判据 | 它拦的是 |
| --- | --- | --- |
| **静态线** | 月度总量 ≥ 额度 × `THRESHOLD`（默认 80%） | 爬得慢，但爬到了 |
| **突发闸门** | 按最近半小时的速率算，剩余额度撑不过 60 分钟 | 爬得快，总量还来不及越线 |

约 630 行 JavaScript，唯一的运行时依赖是 4 KB 的 [`aws4fetch`](https://github.com/mhart/aws4fetch)。无状态、无网页界面、不主动通知任何人——最后一点是刻意的，见[补上两道 AWS 侧的防线](#5-补上两道-aws-侧的防线必做)。

> [!IMPORTANT]
> **适用范围：整个 AWS 账号里只有一台 Lightsail 实例，且长期存在、按月正常扣费。**
>
> 多实例、混合规格、跨可用区、月中创建导致额度按天折算——都**不在设计范围内**。打破前提时读数会**静默低估**，两道线一起失效且日志里不留痕。用之前请先读[适用范围](#适用范围)确认你的情况符合。

## 快速开始

### 1. 建 IAM 用户

创建一个只给这个 Worker 用的 IAM 用户，附上下面这份策略，然后生成 access key。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "LightsailBandwidthWatchdog",
      "Effect": "Allow",
      "Action": [
        "lightsail:GetInstanceMetricData",
        "lightsail:GetInstanceState",
        "lightsail:StopInstance",
        "lightsail:StartInstance"
      ],
      "Resource": "*"
    }
  ]
}
```

这四个动作正好是[决策表](#决策表)里会出现的全部调用，没有多余的。

`"Resource": "*"` 在[适用范围](#适用范围)内是安全的：账号里本来就只有那一台实例，`*` 和精确 ARN 指向同一个东西。之所以不写成精确 ARN，是因为 Lightsail 的资源 ARN 由自动生成的 GUID 拼成（`arn:aws:lightsail:REGION:ACCOUNT:Instance/GUID`）而不是实例名，实例一旦重建 GUID 就变，策略得跟着改。**但如果你的账号里还有别的、绝不希望被这套东西碰到的实例，收窄权限就不是可选项了：**

```bash
aws lightsail get-instance --instance-name your-instance --region ap-northeast-1
```

### 2. 填配置

编辑 [`wrangler.jsonc`](wrangler.jsonc) 的 `vars`，按[配置项](#配置项)填好 `AWS_REGION`、`INSTANCE_NAME`、`QUOTA_GIB`、`THRESHOLD`。

`QUOTA_GIB` 填你所在区域的实际值，不要照抄别人的：

```bash
aws lightsail get-bundles --region ap-northeast-1
```

### 3. 写入 secret

```bash
npx wrangler secret put AWS_ACCESS_KEY_ID
```

```bash
npx wrangler secret put AWS_SECRET_ACCESS_KEY
```

### 4. 部署

```bash
npm install
```

```bash
npm run deploy
```

**`npm run deploy` 等价于 `npm test && npx wrangler deploy`——测试不过就不部署。** 这不是洁癖：一次坏部署换来的是一个悄悄失效的看门狗，而那正是[下一节](#5-补上两道-aws-侧的防线必做)整节在讲的、最难被察觉的故障。

如果你接了 **Cloudflare Workers Builds** 做 push 自动部署，**面板里的 deploy command 也必须填 `npm run deploy`**，不能是裸的 `npx wrangler deploy`。仓库里那个 GitHub Actions 跑同一套测试，但它只让失败在 commit 和 PR 上可见，**拦不住** Workers Builds——真正的闸门是 deploy command 里那个 `npm test`。

部署后到 *Workers & Pages → 你的 Worker → Settings → Triggers* 确认 cron trigger 已生效，然后看日志：

```bash
npx wrangler tail
```

**第一件该确认的事，是 `OK` 那一行末尾的 `meter ... behind` 真的出现了**，理由见[读日志](#读日志)。

### 5. 补上两道 AWS 侧的防线（必做）

**这个 Worker 不会主动通知任何人，这是刻意的。** 需要讲清楚的不是「停机了我怎么知道」，而是**看门狗自身失效时你怎么知道**——凭据过期、IAM 策略被改、部署损坏、cron trigger 被禁用、Worker 被整个删掉。每一种都让实例继续跑、继续烧流量，而**从外部看，它与「本月流量很平静」完全无法区分**。Worker 说不出这件事，因为它自己就是坏掉的那一方。

所以必须有两个**不依赖它存活**的信号：

**AWS Budgets**（*账单与成本管理 → 预算 → 创建预算 → 成本预算*）。金额设成略高于正常月度支出，在 80% 和 100% 两个点告警到一个你真的会看的邮箱。代价是慢——账单数据有数小时延迟，响的时候钱已经花了一部分。

**Lightsail 实例指标告警**（*Lightsail → 实例 → 指标 → 网络出 → 添加告警*）。阈值按「一个 5 分钟数据点的字节数」设，取一个正常业务绝不会碰到的值。它几分钟内就响，补的正是 Budgets 太慢的那一段。

四道防线各守不同的失效：

| | 谁在判断 | 延迟 | 覆盖 |
| --- | --- | --- | --- |
| Worker 静态线 | Worker | 分钟级 | 月度总量爬到阈值 |
| Worker 突发闸门 | Worker | 分钟级 | 速率突然拉高 |
| Lightsail 指标告警 | AWS | 分钟级 | 速率突然拉高，**且 Worker 已经死了** |
| AWS Budgets | AWS | 小时级 | 钱已经花出去了，**且上面三道全都没拦住** |

## 工作原理

一个 cron trigger，`*/10 * * * *`，每天 144 次。每次触发做的事情是固定的：先量，再让数字决定动作。

> **贯穿全篇的一条原则：停机路径上的每一个不确定性都向「停」倾斜，重启路径上的都向「什么都不做」倾斜。**
>
> 漏停一次的代价是账单，多停一次的代价是站点晚几分钟回来；误启动一台被刻意停下的实例会开始烧流量，少启动一次不会。下面凡是看起来不对称的地方，都是这条原则的结果。

**它是无状态的。** 没有 KV、没有 D1、没有 Durable Object，每次触发都从 Lightsail 指标 API 重新算一遍。所以没有会损坏的存储，一次失败的触发之后也没有任何东西需要对账——下一次触发会独立地把结论重新得出来。

### 测量

用 `GetInstanceMetricData` 分别拉 `NetworkIn` 和 `NetworkOut` 从**本月 1 日 00:00 UTC 到此刻**的数据，`statistics: ["Sum"]`，把所有数据点的 `sum` 累加。数据点既不保证有序也不保证连续，所以是累加而不是按下标取值——求总量与顺序无关，缺口本身就代表那段时间没有流量。

时间基准取 `controller.scheduledTime` 而不是墙上时钟：它精确落在 cron 的时间格上，即便这次调用被延迟或重试，评估的仍然是它当初被触发的那一格。

**进出双向都算。** 只有出向超量才计费，但额度是被两个方向一起吃掉的。

### 决策表

令 `used = (NetworkIn + NetworkOut) / 2^30`，`limit = QUOTA_GIB × THRESHOLD`：

| 情形 | 动作 | AWS 调用次数 |
| --- | --- | --- |
| `used >= limit` | **停机**（实例非 `running` 时跳过动作） | **4**（或 3） |
| `used < limit`，突发闸门跳闸 | **停机**，同上 | **6**（或 5） |
| `used < limit`，速率正常 | 什么都不做 | **4** |
| 总字节 **恰为 0**，实例 `stopped` | **启动** | **4** |
| 总字节恰为 0，实例是别的状态 | 什么都不做 | 3 |
| 总字节恰为 0，但 `MANUAL_HOLD="true"` | 什么都不做，连状态都不查 | 2 |
| `used < limit`，但突发窗口**一个数据点都没有** | 查状态判断是「指标失明」还是「实例没在跑」，前者写 `BLIND`；**不停机** | **5** |

正常日子的基线是 4 次调用：两个指标的月度查询 + 突发窗口的两次查询。第 5 次是 `GetInstanceState`，第 6 次才是真正的动作。总量已经越过静态线时会跳过突发闸门——已经确认要停，没必要再花两次调用去问速率。

### 突发闸门

月初至今是个**滞后的总量**，它看不出「最近半小时正在以 2 Gbps 烧」。默认的 20% 余量在 1 Gbps 下只够烧 29 分钟、2 Gbps 下 15 分钟——并不比一个检测回路长多少。所以除了静态线，每次触发还额外查最近半小时（`period: 300`），算出当前速率，然后问一个动态问题：

> 按这个速率，剩余额度还能撑多久？撑不过 60 分钟就现在停。

**比较的目标是整份额度，而不是 `THRESHOLD` 那条保守的早停线。** 这道闸门问的是「会不会在下一次能反应过来之前冲过配额」，而配额才是开始计费的地方。比到阈值会退化：`remaining → 0` 时任何速率都会跳闸，它就不再是突发探测器，而变成静态线的一个吵闹的复制品。这也意味着**即便把 `THRESHOLD` 设成 `1`，突发闸门照样生效**。

速率是**两个方向各算各的再相加**——每个指标的字节数除以它自己实际落库的点数 × 300 秒。三件事各有理由：

- **不除以窗口长度。** 指标有几分钟延迟，窗口尾部通常还是空的；拿整个 1800 秒去除会把速率算低——而算低正是不安全的那个方向。
- **不用共同分母。** 两个指标的落库进度不保证同步。`NetworkIn` 落了 6 个桶而 `NetworkOut` 只落了 2 个时，取较长的当分母，会把出向那 600 秒里的字节摊到 1800 秒上，速率报低三倍——一场 2 Gbps 的突发就这样被放行。
- **也不取较短的。** 某个方向一个点都没落时分母会归零，闸门整个失效。

**窗口不钳到月初。** 速率是个物理量，跨过 00:00 UTC 那一刻实例并没有变慢；跟着月度窗口一起钳的代价是每个月头 5 分钟闸门凑不满一个数据桶、完全失明——而那恰恰是额度刚重置、最可能有人开始猛跑的时候。

### 「恰好零字节」是查询状态的闸门

一台运行中的实例几分钟内必然产生*某些*流量——DNS、NTP、互联网上的后台扫描——所以「月初至今总量为零」等价于「它没起来」。没有这道闸门，handler 就得在每次触发里都多问一次 `GetInstanceState`，为了每月一次的重启多付约 4300 次调用。总量恰为零时也不可能有突发，那两次窗口查询同样省掉。

这个假设有个前提：**指标响应本身是可信的**。所以指标读不懂时必须抛错而不是折算成 0——否则「零字节」就不再只意味着「它没起来」，还可能意味着「我没看清」。

### 幂等，以及它的边界

停机前先查状态，所以第二次触发不会对一个已经停下（或正在停）的实例再发一次停机。重启只在总量恰为零且状态为 `stopped` 时发出。

**但那次状态查询不是停机的前置条件。** 一旦确认越线，`GetInstanceState` 读不出结果时会**照停不误**，只在日志里留一行 `DEGRADED`。它存在的意义只是幂等；让它的失败中断整轮，等于让一次已经确认的越线白白漏掉一个 cron 周期。

重启路径相反：读不到状态就**抛错，不启动**。

### 你自己在月中停掉的实例不会被它拉起来

那时计量表上已经有流量，总量不为零，重启分支根本不会进。它要等到跨月、读数归零之后才会接手这台实例——如果那时你仍然不希望它被启动，就设 `MANUAL_HOLD`。

### 错误处理

任何非 2xx 的 Lightsail 响应都抛出异常，向上冒到 Workers，把这次调用记为失败。异常消息里会把**两个凭据都**抹成 `[redacted]`（先脱敏再截断，否则凭据正好横跨 500 字节边界时会残留半截）——SigV4 的拒绝响应会回显包含 access key id 的 credential scope；secret 按理不会被任何 AWS 响应回显，但「按理不会」不是把它排除在外的理由。

签名客户端配了 2 次重试，只针对 5xx 和 429。有两个瞬时错误落在外面，是[刻意接受的](#计费与限流)。

**读不懂的响应一律抛错，绝不折算成 0。** 0 字节是**唯一**会让看门狗什么都不做的读数，把「读不懂」静默折算成 0，就等于让指标侧的一次降级换来一个一边报平安、一边放任实例烧到超额的看门狗。具体判据见[编码时的坑](#编码时的坑)。同理，`sum` 只要出现就必须是有限的非负数字——JSON 里 `"500"` 是合法值，而 `bytes += "500"` 会走字符串拼接，两个 500 GiB 的桶会被读成 0.005 GiB。

## 读日志

每次触发写**一行**，行首是 `实例名@区域` 加一个状态标记：

```
your-instance@ap-northeast-1 OK | used 137.482 GiB (13.4% of 1024) | stop at 819.200 GiB | now 4.3 Mbps, 20.5 d to quota | month 47% elapsed, projected 294 GiB | meter 1.5 min behind
```

带上区域是因为实例名只在单个区域内唯一——日志要能独立说明自己出自哪个部署。

状态标记是给 grep 用的：

```bash
npx wrangler tail --format pretty | grep -v " OK | "
```

| 标记 | 含义 | 级别 |
| --- | --- | --- |
| `OK` | 两道线都没碰到 | log |
| `STOPPED` | 已停机，后面跟着触发的是哪一道 | **error** |
| `STARTED` | 额度读数归零且实例处于停机，已启动 | log |
| `DOWN` | **看门狗把它停下了，现在还停着。** 两条停机路径的稳态收敛到这一个词 | log |
| `NOOP` | 该做的事已是既成事实（读数为零但实例在跑） | log |
| `HOLD` | 本该启动，但 `MANUAL_HOLD` 拦住了 | log |
| `BLIND` | 突发闸门这一轮看不见：数据太旧，或者窗口里一个点都没有而实例确实在跑 | **error** |
| `DEGRADED` | 状态查询失败，但已确认越线，照停不误 | **error** |

`OK` 那一行的每个字段各回答一个问题，而且全部是这一轮**已经算出来**的东西，没有为日志多花任何一次 API 调用：

| 字段 | 回答的问题 |
| --- | --- |
| `used 137.482 GiB (13.4% of 1024)` | 我在哪 |
| `stop at 819.200 GiB` | 线在哪 |
| `now 4.3 Mbps, 20.5 d to quota` | **突发闸门这一轮读到了什么。** 不露出来的话它在正常运行里完全不可见，没人能确认它还在工作 |
| `month 47% elapsed, projected 294 GiB` | 照这个月的平均速度，整月会用到多少。月初 15 小时内样本太短，这个字段会省略 |
| `win 6/6` | 突发窗口实际拿到几个桶 vs 满窗。**这才是「数据够不够新」的可用指标**——它一掉就掉一格 |
| `days 16/22` | 月度读数拿到几个天桶 vs 本月已过几天。差值有正当解释（实例合法停机的日子没有桶），所以只记录不告警 |
| `meter 1.5 min behind` | 最新的桶还在不在。**注意它的分辨率只有一整个 300 秒桶**，见下 |

几个值得认识的读数：

- `now 0 kbps, never to quota`——最近半小时确实**有数据点，且都是零**，实例是醒着的但没有流量。
- `now unknown (no data points in window)`——窗口里**一个数据点都没有**，速率无从谈起。这和上一条是两件事，绝不能混：前者是「测到了零」，后者是「没测到」。若同一轮还有一条 `BLIND`，说明实例在跑而指标看不见；若没有 `BLIND`，说明实例本来就没在跑。
- `now 143.2 Mbps (stale), ...`——**速率带 `(stale)`**，说明数据老过了 12 分钟的容忍上限，同一轮里必定还有一条 `BLIND`。这个数不能当正常读数看。
- `projected 1497 GiB`——静态线还没碰到，但趋势已经越过 1024 的额度。这是最早能看出问题的字段。

> [!IMPORTANT]
> **`meter` 不是落库延迟的测量值，别把它当验收标准。**
>
> `lagSeconds = endTime − (newest + 300)`，而 `newest` 是最新桶的**起点**。生产的 `endTime`
> 永远落在 300 秒网格上（cron 是 `*/10`），而实测表明桶在关闭那一刻就已经可查——于是
> `newest` 恒等于 `endTime − 300`，整个表达式**恒为 0**。它只能取 0/5/10/15… 分钟这几个值，
> 量化到一整个桶，真实延迟（几十秒）整个落在第一格的死区里。
>
> 换句话说它测的是「最新的桶还在不在」，不是「数据有多旧」。更早的版本把「跑上一天、
> `meter` 稳定在 10 分钟以内」写成部署验收标准——**那条标准会永远通过**。
>
> 真正有分辨率的字段是 **`win N/M`**：延迟一旦超过一个桶，它先掉到 5/6。
>
> 副作用：`MAX_TOLERABLE_LAG_SECONDS = 720` 落在两个可能取值（600 和 900）之间，所以实际
> 生效的门槛是 **900 秒**而不是 720。`tuning.test.js` 里那套 840 秒的推导，离散化之后没有
> 它看上去那么精确。

## 配置项

两个 secret 用 `wrangler secret put` 设置，其余写在 [`wrangler.jsonc`](wrangler.jsonc) 的 `vars` 里。

### Secret（绝不写进 `wrangler.jsonc`）

| 名称 | 说明 |
| --- | --- |
| `AWS_ACCESS_KEY_ID` | IAM 用户的 access key id |
| `AWS_SECRET_ACCESS_KEY` | 对应的 secret access key |

两者都只做「存在性」检查，值不会离开签名函数，也不会出现在任何日志或异常消息里。

### 变量

| 名称 | 必填 | 说明 |
| --- | --- | --- |
| `AWS_REGION` | 是 | 实例所在区域，例如 `ap-northeast-1`。它同时决定 API endpoint、签名 region，以及日志前缀的后半截 |
| `INSTANCE_NAME` | 是 | 实例名（控制台里显示的那个，不是 ARN、不是主机名）。和 `AWS_REGION` 一起构成日志前缀 `实例名@区域` |
| `QUOTA_GIB` | 是 | 套餐的月度流量额度，单位 GiB。必须是正数，且不能大到让字节数溢出安全整数范围（约 8 PiB）。取值见[单位](#单位为什么全都是-gib) |
| `THRESHOLD` | 是 | 静态停机线，必须是 **(0, 1] 的小数**。写成 `80` 会在启动时被拒绝。设为 `1` 表示**用满整份额度才停**，即恰好停在开始超额计费的那一刻——**不是**「不再停机」 |
| `MANUAL_HOLD` | 否 | 设为字符串 `"true"` 时抑制所有 `StartInstance`。**只认精确的 `"true"`**，`"True"`、`"yes"`、`"1"`、前后带空格都视为未设置。停机行为不受它影响 |

`AWS_REGION` 与 `INSTANCE_NAME` 还额外拒绝字面值 `CHANGE_ME`——占位符是非空字符串，能骗过「必填项缺失」那道检查，然后每天在 Lightsail 侧失败几百次。这个检查是**精确比较**：真有人的实例叫 `change_me_later`，那是别人正经的实例名，不能拦。

**任何一项校验失败都是硬错误，在发出任何 AWS 请求之前抛出。** `Number("1,024")` 是 `NaN`，而与 `NaN` 的任何比较都是 false——`used < limit` 为 false 会被读作「已超额」，于是实例被立刻停掉。所以每个数值变量都必须在第一次触发时大声失败，而不是套用某个静默的默认值继续跑。

### 单位：为什么全都是 GiB

`QUOTA_GIB` 填的是 **GiB（2^30 字节）**，直接照抄 `GetBundles` 返回的 `transferPerMonthInGb`：1 TB 套餐填 `1024`，2 TB 填 `2048`，不需要任何换算。

这个结论来自字段命名的一致性推断，而不是明文定义——**AWS 从未说明 `InGb` 这类字段的字节含义。** 依据有两条：`GetBundles` 把宣称的「1 TB」记为 `1024`、2 TB 记为 `2048`（前缀按二进制缩放）；同一份响应里还有 `ramSizeInGb: 0.5`，而 0.5 GB 内存只可能是 512 MiB。

**即便这个推断是错的，默认配置依然安全。** 默认停机线 `1024 × 0.8 = 819.2 GiB ≈ 879.6 × 10^9 字节`：若 1 TB 指 2^40 字节，占额度 80%；若指 1024 × 10^9 字节，占约 85.9%。两种解释下都没有超额——这套换算的安全性不依赖推断成立。

**额度规则里另外几条**，它们决定了代码里每个数字的含义：

- 额度在**同一区域、同一 `bundleId`** 的实例之间汇总。同规格的 IPv4 与 IPv6 实例计入同一份。
- 删掉实例再新建**不会**重置额度，已产生的超额费用也不会消失。
- **部分区域的套餐额度只有其它区域的一半**：孟买、悉尼、雅加达、马来西亚、香港、圣保罗。
- 月中创建的实例当月额度按天折算——**本项目不处理**，见[适用范围](#适用范围)。
- 额度在每月 1 日 **00:00 UTC** 重置。Worker 全程用 UTC 算月份边界，不碰本地时区——两者不是同一个时刻，用错会让每个月有最多一天的时间查错窗口。

## 参数是怎么定的

四个可调的数，各自被什么夹住。下面的算例都以一台 1 TB 套餐的实例、指标落库延迟按 10 分钟的悲观值为前提。

### `THRESHOLD = 0.8`（静态线）

不能再高，因为[单位](#单位为什么全都是-gib)那节的安全性论证依赖它：

| `THRESHOLD` | 停机线 | 若 1 TB = 2^40 | 若 1 TB = 1024×10^9 |
| --- | --- | --- | --- |
| 0.80 | 819.2 GiB | 80.0% | **85.9%** |
| 0.85 | 870.4 GiB | 85.0% | 91.3% |
| 0.90 | 921.6 GiB | 90.0% | **96.6%** |

0.9 在悲观解释下只剩 3.4% 余量，连指标延迟都盖不住。

反过来也不该调低：**静态线触发不算「过早停机」**——它响的时候你确实已经用掉了 80% 的额度。真正可能误停的是突发闸门，那是另一个旋钮的事。

### `REACTION_HORIZON_SECONDS = 3600`（反应视野）

这是闸门**唯一的灵敏度旋钮**，判据等价于 `速率 > 剩余额度 ÷ 视野`。60 分钟意味着空表时要约 2.4 Gbps、用到 800 GiB 时要约 534 Mbps 才跳闸——对一台个人站实例，两个数都远在正常业务之上。想更保守就调大它，代价是可能掐掉一次合法的大流量传输（备份、迁移、直播）。

**这个数是跟着 cron 走的，不是独立选的。** 检测回路 = 桶关闭（≤ 5 分钟）＋ 落库延迟 ＋ cron 间隔 ＋ 停机生效（约 1 分钟）：

| 落库延迟 | cron 每 2 分钟的回路 | cron 每 10 分钟的回路 | 30 分钟视野余量 | 60 分钟视野余量 |
| --- | --- | --- | --- | --- |
| 5 分钟 | 13 分钟 | 21 分钟 | 1.43x | 2.86x |
| **10 分钟** | 18 分钟 | **26 分钟** | **1.15x** | **2.31x** |
| 15 分钟 | 23 分钟 | 31 分钟 | **0.97x —— 守不住** | 1.94x |
| 20 分钟 | 28 分钟 | 36 分钟 | 0.83x | 1.67x |

cron 两分钟一次时 30 分钟够用；十分钟一次时回路涨到 26 分钟，同样的 30 分钟只剩 1.15 倍，而落库延迟一到 15 分钟就**跌破 1.0**——额度会在闸门能动手之前烧完。所以取 60 分钟。

### `BURST_WINDOW_SECONDS = 1800`（观察窗口）

两头夹出来的：

- **太长会稀释。** 速率是窗口内的平均值，刚开始 5 分钟的突发在一小时的窗口里只显出真实速率的十二分之一。
- **太短会瞎。** 窗口整个落进落库延迟的阴影里就一个数据点都取不到。

跳闸时刻有闭式解。令 λ = 有效可见延迟（落库延迟 + 桶对齐余数），可见窗口长度 `V = W − λ`，`t_exh` = 从此刻起烧完剩余额度所需时间：

| 情形 | 跳闸时刻 | 跳闸时的剩余余量 |
| --- | --- | --- |
| `T ≥ W`（速率不再被稀释） | `t_exh + λ − H` | **`H − λ`，与速率和窗口都无关** |
| `T < W`（仍在稀释区） | `λ + (W−λ)·t_exh/(H+W−λ)` | `t_exh·H/(H+W−λ) − λ` |

> 这一组是数值模拟验证过的（16/16 对上）。更早的版本写的是「余量 = `t_exh·H/(H+W−L)`，与速率无关」——**那个式子是错的**，它漏掉了「月度用量读数本身也滞后 λ」这一项，6 组算例全部对不上。「与速率无关」说的是慢突发那一档的**绝对余量**（≈ H − λ），而不是更早表格里那个「跳闸时耗尽进度 40% / 63%」的**比例**——那个比例实测在 41%–109% 之间剧烈变化。

| 窗口 | 5 Gbps 下跳闸时的剩余余量（实测） | 延迟 20 分钟时还剩几个点 |
| --- | --- | --- |
| 60 分钟 | **−41 秒 —— 配额已经烧完才跳闸** | 8 |
| **30 分钟** | **约 +12 分钟** | **2** |
| 20 分钟 | 更多 | **0 —— 闸门失效** |

> 更早的版本把 60 分钟那一格写成「还剩 7.2 分钟」，那是用上面那个错公式算的；实测是**负数**——把失败写成了「还有余量」。结论（30 分钟优于 60 分钟）不变，支撑它的数字换成了实测值。

30 分钟是这两条曲线的交点。**它只影响反应快慢，不影响灵敏度**——判据里没有 `W`，所以缩短窗口不会让闸门更容易误报。这就是为什么「想更保守」要去动视野而不是窗口。

### `MAX_TOLERABLE_LAG_SECONDS = 720`（延迟容忍上限）

超过它就写一行 `BLIND`。**这个数必须挂在检测回路上，不能挂在观察窗口上**——窗口管分辨率，回路管及时性，两者会在改 cron 时朝不同方向走。

用和视野同一条规则推：回路要留在视野的一半以内，回路里除延迟外的固定部分是 300 + 600 + 60 = 960 秒，于是延迟上限 840 秒。取 12 分钟，比这个上限再早一点，也比「5 Gbps 下真的守不住」的经验临界点（16 分钟）早四分钟。

> 早先它写成 `BURST_WINDOW − 2 × BURST_PERIOD` = 20 分钟。cron 两分钟一次时临界点在 25 分钟，20 分钟的告警是**提前**的，没问题；放宽到十分钟后临界点降到 16 分钟，同一个 20 分钟就变成**迟到四分钟**——延迟落在 [16, 20) 分钟时设计已经失效而没有任何提示。

### cron `*/10`

| cron | 次数/天 | 占 Workers 10 万次/天额度 | AWS 调用/天 | AWS 调用/月 |
| --- | --- | --- | --- | --- |
| **`*/10`** | **144** | **0.14%** | **576** | **17,856** |
| `*/2` | 720 | 0.72% | 2,880 | 89,280 |
| `*/1` | 1440 | 1.44% | 5,760 | 178,560 |

**两边的额度都远远够用**——Workers 免费版每天 10 万次请求，而 Lightsail API 调用[不计费也没有速率配额](#计费与限流)。更快也完全付得起。

选十分钟而不是更快，理由不是额度，是**不希望高频轮询被上游判定为滥用接口**——那不是一条能在文档里查到的线，宁可留出余量。**能省的资源就省一点**，这个 Worker 本来就是为了省钱而存在的。

代价明确记在这里：检测回路从 18 分钟涨到 26 分钟，由视野从 30 分钟提到 60 分钟补回来；[设计成立的条件](#精度与延迟)从「落库延迟 < 25 分钟」收紧到「< 18 分钟」。

### 它们是耦合的

**改 cron 必须回来复核视野和延迟容忍，反之亦然。** 这几个数不是各自独立的，改了一个而忘了其余，代码照样跑、行为照样对、测试照样绿——只是防线悄悄变薄。本项目真的这样错过一次（就是上面那个「迟到四分钟」）。

所以 [`test/tuning.test.js`](test/tuning.test.js) 把 `wrangler.jsonc` 和 `src/index.js` 一起读进来，把这些关系钉死：视野 ≥ 2 × 回路、延迟容忍早于设计失效、延迟容忍早于分辨率失效、容忍延迟下窗口仍有两个数据点。改坏任意一个都会红。

## 上游 API：能力边界与坑

### 精度与延迟

这套东西的反应速度上限不由我们决定，由 Lightsail 的指标 API 决定。

**采样精度：300 秒，已经触底。** 除 `StatusCheckFailed*` 外，所有实例指标只有 5 分钟这一档粒度。`BURST_PERIOD_SECONDS = 300` 不是一个选择，是硬底——`period` 填 60 只会得到空桶。**我们能看到的最快的东西，就是一个 5 分钟平均值。**

**落库延迟：AWS 不公开，但已实测。** 官方原话只到「数据点不会在周期结束的那一刻就可查，具体多久随服务而变」。上面所有的余量标定都以它为输入，所以 Worker 自己量：突发窗口那次查询本来就要拉数据点，取最新那个桶的时间戳减一下就是延迟，零额外调用，每次触发写进日志。

> **实测（2026-08-22）——但更早的版本在这里写错了。** 曾经写着「5 次独立采样一致落在 0.8–0.9 分钟」，那个数**测的不是落库延迟，是 `endTime` 的对齐偏移**：采样时用的是任意时刻，而返回的桶标签跟着 `startTime` 走。
>
> 用对齐的 `endTime`（也就是生产的条件）复测，结论完全不同：
>
> - **300 秒桶在关闭那一刻就已经是终值**，不需要额外等待落库。四个对齐时刻查下来，`newest` 全部恰好等于 `endTime − 300`。
> - **尚未关闭的桶也会被返回**，内容按约每分钟一档增长（+52 秒时还没出现，+68 秒时出现）。
>
> 所以「桶必须先关闭才可查」这条对 300 秒档也不成立。真实的检测回路约 **16 分钟**，而不是下文按 10 分钟悲观延迟算出来的 26 分钟。
>
> 参数**不跟着调小**：按悲观值定意味着真实余量更大，方向是安全的。但那些以「26 分钟回路」为前提的*描述*应当读作保守上界，而不是实测值。

由此可以算出**不可压缩的盲区**：

> 桶必须先关闭（≤ 300 秒）＋ 落库延迟 L ＋ cron 间隔（≤ 600 秒）＋ 停机生效（约 60 秒）

即便 L 为零也有 **16 分钟**看不见，**任何参数都调不到这个下限以下**。换算成实际后果（从空表开始的 5 Gbps 突发——这是 2023-06-29 之后创建的 Lightsail 实例的文档上限；额度 1024 GiB，视野 60 分钟）。

> 下表是**单点估计**。独立审计用离散事件模拟扫遍 cron 相位后发现「只有静态线」那一列系统性偏高约 150 GiB（实测区间例如 L=5 分钟时是 1049–1363 而不是 1465），也就是说它**把闸门的价值说大了**；「加上突发闸门」那一列六行有五行落在实测区间内，是合理的中位估计。结果对相位有 ±350 GiB 的敏感度。

| 落库延迟 L | 只有静态线时烧掉 | 加上突发闸门后烧掉 | 闸门可用桶数 |
| --- | --- | --- | --- |
| 5 分钟 | 1465 GiB **超额** | 809 GiB | 5 |
| 10 分钟 | 1640 GiB **超额** | 902 GiB | 4 |
| 15 分钟 | 1815 GiB **超额** | 1008 GiB | 3 |
| 20 分钟 | 1989 GiB **超额** | 1129 GiB **超额** | 2 |
| 25 分钟 | 2164 GiB **超额** | 1269 GiB **超额** | 1 |
| 30 分钟 | 2338 GiB **超额** | 2338 GiB **超额** | 0 |

三个结论：

1. **几百 Mbps 这一档，静态线单独就够。** 1 Gbps 时越线后最坏再烧 181.6 GiB（= 速率 × (落库延迟 600 + 桶关闭 300 + cron 600 + 停机生效 60) 秒，这是解析上界；实测扫遍起始用量与 cron 相位的最坏值是 146.6 GiB）。204.8 GiB 的余量吃得下。
2. **Gbps 这一档必定超额，而突发闸门救不了最坏情况。** 上表左右两列的差距是闸门在**典型相位**下的贡献；扫遍速率 × 起始用量 × cron 相位之后，**最坏超额有没有闸门几乎一样**（约 513 vs 528 GiB，闸门只移动 10–15 GiB）。原因是最坏情况总是「贴着静态线时来一场极快突发」，而那时静态线在同一格 cron 里就先触发并短路了闸门；闸门只有在静态线还很远时才有机会说话，而那正是剩余额度大、它最不敏感的时候。**唯一能改善最坏情况的旋钮是 `THRESHOLD`**——从 0.8 降到 0.5 能把最坏超额从约 513 GiB 压到约 209 GiB。本项目**刻意不降**：它换来的是中段（2–6 Gbps、起始用量偏低）少 18 次超额，代价是 30 次多余停机，而「不希望被过早停机」同样是硬要求。这个取舍是明确做出的，不是没想到。
3. **设计成立的条件是 L < 约 10 分钟**，不是更早版本写的 18 分钟。独立审计扫遍突发相对 cron 时间格的全部相位后发现：L = 12 分钟时已有三分之一的相位守不住配额，L = 18 分钟时是三分之二。上面那张表给的是单点值，实测对相位有 ±350 GiB 的敏感度（5 Gbps 下一格 cron = 349 GiB，相位不是细节）。**实测（2026-08-22）落库延迟是 0.9 分钟，比这条线宽一个数量级**，见[精度与延迟](#精度与延迟)。但那是一次采样不是分布，所以 `meter ... behind` 这个字段继续存在，**验收标准仍然是：跑上一天，`meter` 应当稳定在 10 分钟以内。**

> [!WARNING]
> **真要防住 Gbps 级别的攻击，护栏不该只放在这里。** 上游 API 从物理上就喂不动一个那么快的控制环——16 分钟的盲区下限摆在那里。那一档的正确做法是在实例前面加限速（Cloudflare 代理、防火墙规则），把这个 Worker 留作最后一道兜底。

### 已实测：`period: 86400` 会返回「今天」的部分聚合

这曾经是整个项目最大的未验证点，一度被判为可能致命：月度查询用 `period: 86400`，桶是一整天——如果 API 只返回**已关闭**的天桶，月度读数就对「今天」完全不可见，盲区最长 24 小时。那样的话静态线整天看着昨天的读数，突发闸门的剩余额度纹丝不动，一场 300 Mbps 的中速燃烧可以烧满一整天。

**实测结论：不存在这个盲区。** 2026-08-22 03:48 UTC 对真实实例查询「月初至此刻、`period: 86400`」，返回的最新桶是：

```
2026-08-20T00:00:00Z  sum=3130984833
2026-08-21T00:00:00Z  sum=6930673489
2026-08-22T00:00:00Z  sum=893584166   ← 今天，部分聚合
```

也就是说「桶必须关闭后才可查」这条只适用于 300 秒那一档，**不适用于日粒度查询**。

即便如此，下面这两条月度读数新鲜度告警仍然保留——它们零额外调用，而且能在 AWS 哪天改变这个行为时立刻响：

- **月度读数没覆盖到今天** → 写一行 `BLIND | month-to-date reading only covers through …`
- **月份已过数小时、实例在跑、读数却仍是零** → 写一行 `BLIND | … into the month, instance is running, yet month-to-date reads exactly zero`

换个区域或换个时间想自己复核一遍，一条命令就够——看最新数据点的 `timestamp` 是不是今天：

```bash
aws lightsail get-instance-metric-data --instance-name YOUR_INSTANCE --metric-name NetworkOut --start-time $(date -u +%Y-%m-01T00:00:00Z) --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) --period 86400 --statistics Sum --unit Bytes --region YOUR_REGION
```

### 计费与限流

- **Lightsail API 调用不计费。** 计费 FAQ 逐项列举了全部收费项——实例套餐、数据库、块存储、负载均衡器、证书、静态 IP、域名、DNS 查询、快照——**没有 API 请求这一项**，指标与监控也完全没有作为收费项出现。唯一按请求计费的是 DNS 查询（每月 300 万免费，之后 $0.40/百万），与本项目无关。
- **不会带来 CloudWatch 账单。** CloudWatch 确实按 $0.01/1000 次收 `GetMetricStatistics` 这类请求的钱，但那是 CloudWatch 自己的 API；本项目调的是 `lightsail:GetInstanceMetricData`，走 Lightsail 的计费口径。（这一条只有「文档没列」这个否定证据，**建议下个账单周期按服务看一眼有没有意外的 CloudWatch 条目**——那是唯一的正面确认方式。）
- **没有任何 API 速率配额。** Lightsail 的服务配额表里 19 项全是资源数量（实例、磁盘、分发、DNS 区域……），没有「每秒请求数」之类的条目。本项目的速率是 **0.0067 次/秒**（144 次触发 × 4 次调用 ÷ 86400 秒；按每次触发 6 次调用的上限算也只有 0.010）。
- **状态码有两份说法，都要认。** 按操作的错误列表把 `AccessDeniedException` 记为 **400**，Common Errors 那份记为 **403**；`NotFound`/`InvalidInput`/`OperationFailure` 是 400，`ServiceException`/`InternalFailure` 是 500，`ServiceUnavailable` 是 503。「只重试 5xx 和 429」在这三档上都是对的：400 与 403 都是终局失败。
- **两个瞬时错误落在重试之外**：`ThrottlingException` 是 **HTTP 400**（AWS 自己都注明「SDK 会自动重试这个异常」），`RequestTimeoutException` 是 **408**。**这是刻意接受的**：本项目的速率离任何限流阈值有三个数量级，代价只是丢掉一个 cron 周期（10 分钟）——handler 无状态、下次触发会独立重新得出结论，静态线还有 204.8 GiB 余量兜着。真发生了日志里会写明 `HTTP 400 {"__type":"ThrottlingException"...}`，一眼可辨。

### 编码时的坑

- **请求字段是小驼峰**（`instanceName` 而不是 `InstanceName`），与多数 AWS JSON API 相反。写错只会得到一个毫无提示意义的 400。
- **时间戳走 Unix 秒**，不是 ISO 字符串。多乘或少乘一个 1000 是这里的经典 bug——秒级时间戳是 10 位，毫秒级是 13 位。代码同时防两种：不是数字、以及**是数字但量级明显不对**。后者此前没防，结果是毫秒时间戳会让延迟算成巨大的负数、被钳到 0——staleness 检测整体失效，而日志还宣称数据很新鲜。
- 协议是 **JSON 1.1**，靠 `X-Amz-Target: Lightsail_20161128.{Operation}` 分发操作，不是靠 URL path。
- **`period` 必须是 60 的倍数**，范围 60–86400。本项目用两个：月度查询取上限 86400，突发闸门取 300。**填 60 不会报错，也不会得到空桶**——返回的仍是原生的 300 秒数据点，只是不会更细（更早的版本写「只会得到空桶」，是错的）。
- **返回的 `timestamp` 不是原生桶的起点，而是查询窗口自己的分格**（≈ `floor(startTime/60)*60 + k*period`）。实测把 `startTime` 依次偏移 60/120/180/240 秒，标签跟着平移，且整整少掉一个原生桶。生产之所以对得上，是因为 `controller.scheduledTime` 精确落在 cron 网格上、`endTime % 300 == 0`——**这是个隐式前提，没有测试钉住**。
- **数据点保留期随粒度变化**：60 秒粒度 15 天，300 秒粒度 63 天，3600 秒粒度 455 天。本项目两个窗口用的底层数据都是 300 秒那一档，63 天绰绰有余。
- **数据点的有无，对应实例有没有在产生流量。** 实测：一台**运行中**的实例，300 秒桶连续无缺口（整天 288/288），`sum` 最小值约 **77 KB**——DNS、NTP、后台扫描确实一刻不停。而**没有产生流量**的那段时间**一个数据点都没有**（不是 `sum: 0` 的点，是根本不返回）。
  - **一处需要说清的界限**：后半句的观察对象是「这台实例还不存在数据的历史时段」，**不是一台停机中的实例**——不能为了验证它去停生产实例。两者形状很可能相同，但前提不同，这一条至今没有直接实证。
  - 附带结论：速率的分母（`落库点数 × 300`）在正常情况下就等于整个窗口长度。
  - 顺带更正一处旧推理：代码注释曾说「缺口本身就代表那段时间没有流量」——对一台跑着的实例，缺口根本不会出现；累加而非按下标取值的真正理由是数据点**不保证有序**，那一条仍然成立。
- **空数据不是错误，而且「空」有两种长相。** 窗口内没有流量时 HTTP 仍是 200，但响应可能返回 `metricData: []`，**也可能把这个字段整个省掉**——AWS 的响应定义没有保证它必然出现，各语言 SDK 一律把「字段缺失」正规化成空数组。所以「这份响应读不懂」的判据绝不能挂在 `metricData` 存不存在上；本项目挂在 `metricName` 是否正确回显（有值的标量必然被序列化，不像空集合那样可省），两个信号有其一就认定响应是真的。**把「字段缺失」当成错误的代价是致命的**：一台停机的实例在新月份读到的正是这种空响应，于是每次触发都抛错，重启永远发不出去。
- **`instanceName` 有格式约束**：`\w[\w\-]*\w`。本项目**不**校验它——AWS 那个 `\w` 是否含 Unicode 无从确认，照猜写正则的风险是把一个 AWS 明明接受的实例名挡在门外，而那正是占位符检查刻意避免的错误。写错名字会在第一次触发时以 400 响亮地失败。

## 适用范围

这不是「已知限制，以后会修」，是**设计前提**。不符合就别用，或者先改代码。

**前提两条：**

1. **整个 AWS 账号里只有一台 Lightsail 实例。** 不是「该区域该规格只有一台」——就是一台。
2. **它长期存在，按月正常扣费。** 不在月中创建、不删了重建。

**明确不在范围内：**

| 情况 | 为什么不做 |
| --- | --- |
| 账号里有多台实例 | 额度按「区域 + `bundleId`」汇总，而 Worker 只读 `INSTANCE_NAME` 那一台。要正确统计就得先 `GetInstances`、再按区域和规格分组求和，还要处理每组各有一份额度、各需一条停机线——复杂度远超它守的那笔钱 |
| 混合规格 | 同上。不同 `bundleId` 各有各的额度，等于要同时维护 N 条独立的防线 |
| 跨可用区 / 跨区域 | 同区域内换 AZ 不影响额度汇总，等价于多实例；跨区域是另一份额度、另一个 endpoint，需要另一个部署 |
| 月中创建实例 | 当月额度按天折算，而 `QUOTA_GIB` 是静态值——那个月的停机线会偏高 |
| 第一个月额度没发满 | 同上，同一类问题。**不管** |

这些都能做，只是复杂度和收益不成比例。本项目选择把范围收窄到「一台、长期、按月」，然后在这个范围内把事情做扎实。

**打破前提的后果：读数会低估，而且是静默的。** 这是所有失效模式里最难察觉的一种——静态线和突发闸门读的是**同一个**被低估的数字，两道防线会一起失效，不存在互相兜底；它也不像别的故障那样会在日志里留痕，你会看到一行行「一切正常」，直到账单出现。Worker 自己说不出这件事，因为它看到的世界里确实只有那一台实例。

这也是[为什么 AWS Budgets 是必做项](#5-补上两道-aws-侧的防线必做)：它按整个账号的真实账单触发，不依赖 Worker 对世界的认知是否正确。

**开第二台实例之前，先回来读这一节。**

## 设计取舍

这一节解释的是「为什么不那样做」。

**重启由用量驱动，而不是按日期。** 停机只发生在用量越线时，所以当月剩下的时间里用量会一直卡在阈值之上。「用量回落到阈值以下」与「每月 1 号」捕捉的是同一个事件，但前者没有那个仅 24 小时的窗口。按日期驱动的版本有个安静的失效模式：1 号那天恰好凭据过期或 AWS 抽风，重启就错过了，实例一直停到下个月。

**`MANUAL_HOLD` 与 `"true"` 精确比较。** 打错字时（`"True"`、`"yes"`、`"1"`）重启逻辑仍然有效。方向是刻意选的：一个失效时默认放行的锁是可以补救的；而一个因为笔误就生效的锁，会把实例摁在那里，直到有人发现站点不见了。

**`THRESHOLD` 上界卡在 1**，是为了让「按百分比写成 `80`」在启动时就被拒绝。不校验的话它会变成 81,920 GiB 的停机线——一个永远够不到的上限，也就是一个看起来在跑、实际什么都不做的看门狗。`QUOTA_GIB` 的上界（约 8 PiB）出于同一个理由：再大乘上 2^30 就溢出成 `Infinity`，效果一样。

**没有运行时的「关闭保护」开关。** 一旦越线，就没有任何办法让实例照常跑下去。`MANUAL_HOLD` 抑制的是启动而不是停机；手动去控制台把实例启动起来，也只能换来十分钟。

`THRESHOLD = 1` 已经是能配出来的最宽松的一档，而它是「用满整份额度才停」，不是「不再停机」。**如果你确实决定「宁可认了超额费用也不能让站点下线」，这个配置项给不了你想要的东西**——唯一的办法是改代码或者把 cron trigger 停掉，两件都会留在 `git log` 或 Cloudflare 的配置历史里。

运行时开关会友好得多。但**一个能关掉保护的开关，就是一个会被忘记打开回来的开关**；而一个从三月起就被悄悄禁用、无人看管的账单护栏，恰恰是这个 Worker 存在所要防止的场景。

**停机不是应用层的优雅关闭。** `StopInstance` 从实例角度看等同于断电。如果工作负载需要把状态刷到磁盘，就把 `THRESHOLD` 设低一些，给自己留出反应余地。

**安全裕度绝不来自单位换算。** 想要更大的静态余量就调低 `THRESHOLD`。藏在换算里的缓冲既写不进配置也读不出来——半年后没人能说清那个数字是怎么来的。

**只用一个 cron trigger。** Workers 免费版对每个账号的 cron trigger 数量有限制，而这个 Worker 只需要一个：重启逻辑是在同一个 handler 内部分支处理的。**能省的资源就省一点**——这个项目本来就是为了省钱而存在的。

**月度查询的 `period` 取 86400。** 每个指标返回约 31 个数据点；突发窗口那半小时用 `period: 300`，最多 7 个点。理由只是数据点少、解析便宜。

> **更正：这里原先写着「按小时会返回约 744 个点，光解析那份 JSON 就会撑爆 10 ms 的 CPU 预算」——这个说法是错的**，跨模型审计证伪，实测确认。
>
> 而且**用本机跑 `JSON.parse` 去推断 Workers 运行时的耗时本身就没有意义**——两个运行时的性能无从比较。真正的依据是线上数据：**每次触发的 CPU 时间 P50 1.68 ms、P99 2.57 ms**，免费版上限 10 ms，用掉约四分之一。
>
> 结论是**不要为了省 Workers 的 CPU 时间牺牲别的东西**。`period` 保持 86400 是因为[实测确认了它没有当天盲区](#已实测-period-86400-会返回今天的部分聚合)，不是因为 CPU。

**`workers_dev` 与 `preview_urls` 都关掉。** 这个 Worker 没有 `fetch` handler，公开 URL 只会返回错误——还会给一个专门用来压低流量的东西招来流量。

## 测试

```bash
npm test
```

98 个用例，跑在裸 `node --test` 上，纯逻辑，不联网，不碰 AWS。打桩 `globalThis.fetch` 端到端地跑整个 handler——请求确实经过 `aws4fetch` 真实签名，但没有任何东西离开本进程。

打桩按 `period` 区分月度查询和突发窗口，两者能分别给量。这一点是必需的：否则「本月用了 800 GiB」会被当成「最近半小时烧了 800 GiB」，突发闸门在每个用例里都会误触发。

四层，各自回答不同的问题。

### 一、例子测试

`month.test.js`、`scheduled.test.js`。逐条锁住具体行为。有几条锁的是**失败的方向**而不是成功路径，它们是这套东西最该被守住的性质：

- 指标响应读不懂时抛错，而不是折算成 0（合法的空数组、缺席的字段仍然按零处理）
- `sum` 是字符串或负数时抛错，而不是走字符串拼接把用量少报几个数量级
- 已经越线时状态读不出来，照停不误；打算重启时状态读不出来，抛错而不是启动
- 突发速率按每个方向各自实际落库的点数计算，不按窗口长度，也不用共同分母
- 某个方向零数据点时贡献 0，而不是让整个闸门失效
- 每行日志都以 `实例名@区域` 加状态标记开头；速率来自过旧数据点时必须带 `(stale)`
- 突发窗口一个数据点都没有时，**绝不打印 `0 kbps` 这种伪造读数**，而是写 `now unknown`；实例在跑（或状态读不出）就报 `BLIND`，实例没在跑就安静
- 有数据点但时间戳读不出来时同样报 `BLIND`——速率还算得出，但「数据有多新」无从判断，失明检测就此失效
- 凭据在错误响应里出现多次时必须**逐一**抹掉（失败夹具刻意各回显两次——只回显一次的话 `replaceAll` 和 `replace` 无从区分）
- 用量**恰好等于**停机线时必须停机

`month.test.js` 刻意把时区设成 `America/Los_Angeles`。每条断言都针对精确的 epoch 值，所以它们在任何时区下都成立；但**一个改用本地时间辅助函数的实现，在 `TZ=UTC` 下会碰巧通过**。正是这个时差让它们具备鉴别力。

### 二、性质测试

`invariants.test.js`。靠人列举组合是不够的——本项目每换一个 review 视角就会冒出新问题，那本身就是证据。这一层反过来做：随机生成 1500 个场景，断言一组**从需求推出来、而不是从实现抄下来**的不变量。

生成是**分层轮转**的，不是纯随机：`restart / boundary / burst / failure / random` 各占五分之一。纯随机下「`MANUAL_HOLD` 且用量为零且实例 stopped 且没注入故障」这类组合的概率只有约 0.2%，靠加大样本量去赌不可靠。生成维度包括 AWS 侧失败（400 / 403 / 500 分开——只有 500 会被重试）、畸形响应、精确落在停机线上的用量、两个方向落库进度悬殊。

断言的不变量：越线且实例在跑必须停机、启动只在「用量为零 + stopped + 无 hold」时发生、绝不同时停机与启动、凭据绝不出现在任何日志行或异常消息里、畸形响应必须**有意地**抛错（TypeError 不算——那只是碰巧崩了）、评估窗口必须对应 `scheduledTime`、逻辑操作 ≤ 6 且每个最多 3 次 HTTP 尝试。

同一个文件里还有**单调性与无状态**的性质。其中最重要的一条是独立审计指出的、此前**缺失**的那个：

> **看门狗对自己的评价必须随落库延迟单调不减**——数据越旧，它不得越乐观。

违反它的正是那个最严重的缺陷：可观测延迟有天花板（窗口 30 分钟 − 粒度 5 分钟 = 25 分钟），越过之后窗口里一个点都落不进来，于是延迟算不出来、失明检测跟着失效，而速率被当成 0 打进日志——**25 分钟报警并停机，26 分钟静默放行并主动宣称「没有流量」**。

**变异测试结构上抓不到这一类缺陷**：缺的是一整段代码，没有哪一行可以被变异成「不报警」。只有把两次运行按延迟排起来比才看得见。这条性质现在锁住了它（回退修复会让它变红，验证过）。

另外三条（用量/速率越高不该更不容易被停、阈值越低不该更不容易被停、同一 tick 判两次结论一致）保留原样。

> **诚实标注：另外那三条目前没有独立的检出贡献。** 加进来时的设想是「比较符号写反在单点上看不出来」，但归因实验证伪了——注入符号翻转时率先变红的是一批例子测试；注入一个刻意构造的**非单调**缺陷时，抓到它的是随机场景那一层。留着是因为它们把方向性需求写明了、成本也低，但**不能把它们算进「这套测试有多强」的证据里**。

### 三、调参耦合检查

`tuning.test.js`。见[它们是耦合的](#它们是耦合的)。把 `wrangler.jsonc` 和 `src/index.js` 一起读进来验关系，三种断裂都实测会变红。

### 四、变异测试

```bash
npm run mutate
```

**这一层存在的理由是：「测试通过」证明不了测试有用。** 这个仓库里出现过真实的反例——打桩把 AWS 的**合法**空响应当成畸形响应，夹具和断言互相印证了同一个错误假设，全部用例照样绿。

> **但它有一类结构性盲区，必须知道：变异测试找的是「写错的代码」，抓不到「缺失的代码」。** 本项目最严重的那个缺陷（突发窗口零数据点时静默失明）就属于后者——没有哪一行可以被变异成「不报警」，因为本来就没有那一行。加多少变异体都不行。补上它的是[性质测试](#二性质测试)里那条「自我评价随延迟单调不减」，以及一次**独立审计**。

它往 `src/index.js` 里注入 34 个已知缺陷（速率改回共同分母、静态线 `>=` 改成 `>`、只脱敏 access key id、去掉 `QUOTA_GIB` 上界、把视野调回与 cron 不匹配的旧值……），**跑整个套件**逐个确认会变红——只跑其中一层等于给另一层的覆盖打了白条。有变异存活就退出非零。

脚本里的三条纪律都是踩过坑之后加的，而且每一次踩坑的表现都是**静默地一律输出「通过」**：

1. **全程在临时副本里操作**——曾有一次中断把变异留在了 `src/` 里，差点提交上去。
2. **先跑对照组**——干净代码必须是绿的。有一次新加的测试要读 `wrangler.jsonc` 而脚本没复制它，整个套件在副本里报错，19 个变异会全被误报成「抓到」，正是对照组拦住的。
3. **检测器自己也要能被检验**——数行数会被「失败行打两遍」骗到；把 `node --test | grep -q` 放在 `set -o pipefail` 下，管道会返回 node 的退出码而不是 grep 的，整个检测逻辑被反过来；用 `^. tests` 匹配多字节的 `ℹ` 会永远失败。现在直接读汇总里的计数，不依赖任何字形。

### 在本地触发真实的 handler

把凭据写进 `.dev.vars`（已 gitignore，**绝不提交**）：

```
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
```

```bash
npx wrangler dev --test-scheduled
```

在另一个终端手动触发一次：

```bash
curl http://localhost:8787/__scheduled
```

**这会真的调用 AWS API。** 如果目标实例已经超过阈值，它会被真的停掉。请指向一台测试实例，或者临时把 `THRESHOLD` 调高。

## 仓库结构

```
src/index.js                Worker 本体
test/month.test.js          纯函数：月份边界、配置解析、格式化
test/scheduled.test.js      端到端：打桩 fetch 跑整个 handler
test/invariants.test.js     性质测试：随机场景 + 单调性 + 无状态
test/tuning.test.js         调参常量之间的耦合关系
scripts/mutation-test.sh    变异测试（npm run mutate）
wrangler.jsonc              cron trigger、vars、observability
.github/workflows/test.yml  CI：npm test + npm run mutate
```

唯一的运行时依赖是 `aws4fetch`，版本钉死在 `1.0.20`，约 4 KB，负责 SigV4 签名。AWS SDK 对一个 Worker 来说太大了。

纯 JavaScript 加 JSDoc 类型标注，除 Wrangler 原生处理之外没有任何构建步骤。

代码里的日志文本与错误消息保留英文——它们会和 Workers 控制台、AWS 返回的英文报错混在一起，保持一致更便于检索。测试用例名同理。文档正文用中文。
